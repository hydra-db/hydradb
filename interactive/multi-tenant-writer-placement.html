Placing writers for many tenantsfour schemes, one function, two knobs

The four ways you might want writes spread across a fleet are not four designs. They are one function — owner(key, candidates) — with two inputs varied: what goes into the hash, and which nodes are eligible at all. Three of the four need no new mechanism. The fourth needs one small thing, and the shipped design already has a place to put it.

A — what was asked

Four ways to decide which node writes

Multi-tenancy raises the placement question again, in four forms. They look like four features. They are four arguments.

Three terms first, because the rest of the page leans on them. A tenant is a customer: in the code that is a namespace, the first part of a graph's address. A cell is one SlateDB database — a unit of storage that admits exactly one writer at a time, enforced by a writer epoch in its manifest. The writer for a cell is whichever graph-node currently holds that epoch; every other node must send its writes there or be fenced out.

The four schemes, as asked, and the two inputs each one varies:

#What you wantkeycandidate setstate
1 All of one tenant's cells land on a single writer node tenant id alone
(cell omitted)		 all live nodes key change only
2 Every tenant's writes land on one writer node a constant all live nodes key change only
3 Shared cluster: each cell is tied to one writer, so servers stop flip-flopping tenant + cell all live nodes already built, tested, pinned
4 A dedicated writer node per tenant tenant + cell live nodes that serve that tenant needs nodes to advertise what they serve

The whole page is this table, expanded. Nothing outside the two right-hand columns changes between schemes.

Scheme 3 is not a proposal. It is crates/placement/src/hash.rs as it stands on this branch: thirty lines, seven tests, four golden hex values pinned against a Rust unit test. It is also the scheme that fixes the production incident — three graph-nodes taking turns claiming one cell's writer epoch, each one fencing out the last, forever, because nothing in the system decided which of them should be the writer. That story is Placing the writer; this page assumes it.

B — one function

Highest score wins, and the score has exactly two inputs

the whole mechanism owner(key, candidates) = argmaxn ∈ candidates H(key ‖ 0x00 ‖ node_id)
H = FNV-1a 64  ·  ties broken by node id ascending

This is rendezvous hashing: instead of storing who owns what, every node hashes the pair (thing, candidate) for each candidate and picks the highest. There is no assignment table, no election, no lock. Every node that agrees on the candidate list computes the same owner, independently, with no round trip.

In the shipped code the key is two segments, and the signature makes both of the knobs visible — the first two arguments are the key, the third is the candidate set: 

pub fn score(scope: &str, cell_id: &str, node_id: &str) -> u64;
pub fn rank<'a>(scope: &str, cell_id: &str, live: &[&'a str]) -> Vec<&'a str>;
pub fn owner<'a>(scope: &str, cell_id: &str, live: &[&'a str]) -> Option<&'a str>;

crates/placement/src/hash.rs:35, :47, :63 — FNV-1a 64 over scope ++ 0x00 ++ cell_id ++ 0x00 ++ node_id. The 0x00 separator keeps segment boundaries distinct, so ("ab","c") and ("a","bc") cannot collide.

scope today is GraphScope's Display — "{namespace}/graphs/{graph_id}" (src/core/namespace.rs:268–272), so the tenant is already the leading part of the key. owner returning None means placement has no opinion, not nobody may write; the caller's rule is to promote itself when it is the owner or when no owner is live, and to decline otherwise.

C — the key alone

Schemes 1 and 2 are one argument, not one feature

Both are the same call to the same function with a different key. No new storage, no new network call, no new failure mode. In the touch point that decides whether a node may promote itself to writer: 

// scheme 3 — what ships today
placement::owner(&scope.to_string(), cell_id, &live)

// scheme 1 — one writer per tenant: drop the cell from the key
placement::owner(&scope.namespace.to_string(), "", &live)

// scheme 2 — one writer for the whole fleet: hash a constant
placement::owner("_fleet", "", &live)

The signature is unchanged in all three. GraphScope.namespace is a public field (src/core/namespace.rs:227), so the tenant is already in hand at the call site.

Scheme 1 says: two cells of the same tenant must not hash apart, so do not put the cell in the key. Scheme 2 says: nothing must hash apart, so put nothing distinguishing in the key at all — the constant exists only so that the winner still moves when a node dies.

Two honest costs. Neither scheme balances. Rendezvous distributes keys evenly only when there are many keys; with three tenants over four nodes, scheme 1 leaves one node idle in this fixture and there is no rule preventing all three tenants from landing on one node. Scheme 2 is that outcome by construction: one node does every write and the others serve reads. And scheme 1 needs one decision frozen with it — namespaces nest, so "the tenant" is either the root segment or the whole namespace path. Pick one, and it becomes part of the key format, with everything that implies in section G.

D — the candidate set

Scheme 4 is the only one that needs something new

And what it needs is not a mechanism. It is a few characters in an object name.

A dedicated writer per tenant means some nodes must be ineligible for some tenants. The key stays exactly as it is in scheme 3; what changes is the third argument: 

// scheme 4 — same key, smaller candidate list
let candidates: Vec<&str> = live
    .iter()
    .copied()
    .filter(|n| serves(n, &scope.namespace))
    .collect();

placement::owner(&scope.to_string(), cell_id, &candidates)

The only new thing is serves. A node has to state which tenants it will write for, and every other node has to be able to read that statement, because rendezvous only works when all of them compute over the same candidate list.

Put it in the object name, not the object body

Liveness already works by heartbeat: every node PUTs an object under <base>/_graph_nodes/v1/<node-id> every five seconds, and a node counts as live while its object is younger than fifteen. The placement path never fetches those objects. It does one LIST — the object-store operation that returns keys and their timestamps, and nothing else — and works from names and LastModified alone.

That is the property worth protecting. If the served-tenant list lived in the body, computing an owner would need a GET per node on a path that currently needs none, and every one of those GETs would be a chance for the fleet's views to diverge. Putting it in the name keeps the cost at exactly one LIST, unchanged: 

_graph_nodes/v1/graph-node-0.ag     LastModified 2s ago
_graph_nodes/v1/graph-node-1.a      LastModified 1s ago
_graph_nodes/v1/graph-node-2.gi     LastModified 3s ago
_graph_nodes/v1/graph-node-3.i      LastModified 4s ago

a = acme   g = globex   i = initech

The extension point named in docs/plans/2026-07-25-rendezvous-placement.md §3: "if nodes ever serve different cell subsets, encode that in the object name so placement still needs no GETs."

This is not invented here. Sleet, the reference implementation the crate was ported from, already does exactly this: it writes nodes/<node_id>.<letters>.json, where the letters are the services the node offers, sorted and deduplicated (../sleet/src/heartbeat.rs, object_name and parse_object_name). Its rule that unknown letters are ignored on parse is the part to copy — it is what lets a new tenant letter roll out across a fleet one pod at a time without old nodes rejecting the name.

W2 The candidate filter — a LIST, no GETs

Static fallback. Enable JavaScript to change which tenants each node serves.

Try: switch off every node that serves globex. The candidate set empties, owner returns None, and globex has no writer at all until a serving node comes back. Under scheme 3 the fallback is the rest of the fleet; under scheme 4 there is no fallback, and that is the real price of a dedicated node. Note the request counter: it stays at one LIST and zero GETs no matter how the letters change.

E — where a pin belongs

Inside the computation, never beside it

Scheme 4 is the honest answer to "when is pinning a writer actually needed" — it is a real requirement that rendezvous over the whole fleet cannot express. But its shape matters more than its existence.

A pin can live in two places. Inside owner(), as a filter on the candidate set, it is a constraint the function honours, so the router and the node both derive the same answer from the same code. Beside owner(), as an override in the routing layer, it is a second opinion — and two opinions can disagree.

The repository already has the second kind, unused: with_preferred_writer_node on the routing provider. It is harmless today only because nothing enforces ownership yet. Once a node refuses writes for cells it does not own, an override that contradicts placement produces this: 

routing table says        writes for cell-a go to graph-node-2   (override)
ensure_local_writer says  graph-node-2 does not own cell-a       (rendezvous)
                          -> NotCellWriter { owner: graph-node-0 }
driver re-routes to graph-node-0, which the routing table never advertises
                          -> next ROUTE refresh sends it back to graph-node-2

docs/plans/2026-07-25-rendezvous-placement-open-questions.md §B — a routing loop no timeout breaks, from a misconfiguration that validates cleanly.

The candidate filter cannot produce that loop, because there is no second source to disagree with. Routing asks owner(), the node asks owner(), and the filter is inside it. This is the whole reason the current design can absorb scheme 4 later without a redesign — and the reason the answer to "should we keep the preferred-writer override for this" is no. The override and the filter look alike and are opposites.

F — losing a node

What a failure costs differs more than the steady state does

In the steady state the schemes differ in how concentrated writes are, which is visible and easy to reason about. They differ more sharply, and less visibly, in what a single dead node moves — and movement is what costs. Every reassignment is a handover: the new owner opens the SlateDB writer, claims the next epoch, and writes for that cell stall until it does.

Rendezvous has one property that makes any of this tolerable: removing a node does not reshuffle the survivors, so a failure moves only the cells the dead node owned. That is asserted directly in removing_a_node_preserves_the_order_of_the_rest (hash.rs:124–132). The differences below come from the key, not from the hash.

W3 Blast radius — kill a node, count what moves

Static fallback. Enable JavaScript to kill any combination of nodes.

Try: kill graph-node-3. Under scheme 2 every cell in the fleet moves at once, because one node was doing all the writing; under scheme 3 nothing moves, because it owned nothing. That asymmetry is scheme 2's whole risk profile: zero blast radius until the one that matters, then total. Then kill both nodes serving one tenant and watch scheme 4 report cells with no owner while scheme 3 keeps placing them.

G — the frozen key

The catch that applies to all four

A scheme is not a setting. Changing what goes into the hash reassigns the entire fleet at once.

The key is a wire format. Every node computes ownership independently, which only works while every node derives the same string from the same facts. Two versions that build the key differently are two fleets that disagree about who owns each cell — each convinced, each willing to promote itself, which is precisely the incident that motivated the crate. That is why the four hex values are pinned by a unit test rather than merely produced by one:

The hash and its key encoding are FROZEN, like a wire format. Changing either splits a mixed-version fleet into two disagreeing views of who owns a cell, which is the exact failure this crate exists to prevent.

crates/placement/src/hash.rs:8–12

So the schemes are not per-request, per-tenant, or per-deployment options. Moving from one to another is a fleet-wide migration whose cost is the count of cells whose owner changes, each one a writer handover, all of them at the moment the new binary's view wins:

W4 Migration cost — changing the key reassigns the fleet

Static fallback. Enable JavaScript to pick any pair of schemes.

Try: any pair. Note that scheme 4 is the cheapest migration away from scheme 3 — it keeps the key and only narrows the candidates, so cells already owned by a serving node stay put. Note also that no pair is cheap enough to do casually, and that during a rolling restart the two halves of the fleet compute different owners for the moving cells, which is the mixed-version hazard the golden test guards.

Two consequences worth stating plainly. A scheme change needs a migration plan of its own — either a drained flag day, or a versioned key negotiated fleet-wide before it takes effect, which is more machinery than any of the schemes themselves. And whichever key ships first is the one whose golden values get pinned, so the cheapest moment to choose is before anything is running on it.

summary

Take scheme 3, because it is the one you already have

Scheme 3 is built, tested and pinned, and it is the scheme that answers the production incident: one cell, one computed writer, no ping-pong. Nothing about it forecloses the others. Schemes 1 and 2 are the same call with a shorter key, and scheme 4 is the same key with a filtered candidate list, fed by letters in a heartbeat object name that costs no extra request to read.

The thing to carry forward is not the ranking of the four schemes but the shape of the question. Every future placement request — per-region writers, tenant tiers, draining a node before maintenance — arrives as one of the same two knobs, and the useful reflex is to ask which one. If the answer is neither, it is not a placement change; it is a second opinion about ownership, and that is the one thing this design cannot hold without contradicting itself.
