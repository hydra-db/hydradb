Where the time goesThe read and write paths, drawn as they actually run

A structural read of the two hot paths in the kernel: what a write does between the API call and the durable commit, what a read does between the Cypher string and the rows, and the places in that machinery where the cost model is worse than the architecture document implies. Then the harness — benchmarks, flamegraphs, and a Grafana board — to turn each claim into a number.

01 — Orientation

The shape of the thing

Three layers, and every performance question in this note is about which layer a given operation actually lands in.

architecture.md describes a stateless query tier over SlateDB over S3, with memory and NVMe as disposable caches. That is accurate. What it does not describe is the cost model: how many storage round trips one edge write costs, how many one MATCH costs, and what serialises against what. This note fills that in from the code.

Figure 1 — the three layers, and the four caches between them

Red = the structure this note argues is still the dominant bottleneck: one mutex in front of every write in the process. Amber = machinery whose implementation costs more than its shape suggests, including the WAL-tail overlay — once red, now largely fixed (R1) with a smaller residue (R1b). Green = SlateDB's own machinery, which is not the problem.

02 — Write path

What one edge write actually does

Four nested serialisation points, then six to seven strictly sequential storage reads, then a durable commit. The reads are inside the lock.

Take the simplest possible mutation, GraphShard::write_edge. The public entry point validates, checks write authority, and then enters a retry loop that holds two things for its whole duration: a permit from the global graph_write_gate semaphore, and one of 64 writer_lanes mutexes chosen by hashing the cell id. 

src/shard/write.rs:2562
let span = write_txn_span(&mutation.cell_id, Some(&mutation.edge_type));
let _permit = self.acquire_graph_write_permit("write_edge").await?;   // global semaphore
let _writer = self.writer_lane(&mutation.cell_id).lock().await;        // 1 of 64 lanes
for attempt in 0..GRAPH_TXN_MAX_RETRIES {                              // 32
    match self.write_edge_txn(&mutation).await { ... }
}

So far so reasonable — 64 lanes means 64 cells can write concurrently. Except that one level down, write_edge_txn calls acquire_local_write_guard, and that function takes cell_id as an argument and never uses it: 

src/shard/lifecycle.rs:256
pub(crate) async fn acquire_local_write_guard(
    &self,
    cell_id: &str,            // validated, then discarded
    operation: &'static str,
) -> Result<LocalWriteGuard> {
    validate_component("cell_id", cell_id)?;
    validate_component("operation", operation)?;
    let guard = LocalWriteGuard::new(
        Arc::clone(&self.local_write_guard).lock_owned().await   // ONE mutex, whole shard
    );
    self.db.refresh_writer_fence().await?;                          // manifest refresh, inside the lock
    Ok(guard)
}

local_write_guard is a single Arc<Mutex<()>> created once per shard (src/shard/lifecycle.rs:185). Every write to every cell in the process funnels through it. The 64 lanes above it can never do anything but add a second uncontended acquire to the critical path.

Figure 2 — write_edge, from call to durable commit

The ledger for one write_edge. The batch path has the same structure with the per-mutation reads multiplied by batch size — see W5.

The batch path is the single path, N times

write_edge_mutations_batch_txn_locked is where ingest throughput is actually decided, and it is a straight for loop over mutations with an .await per storage lookup inside it (src/shard/write.rs:4166). Per mutation: a GET on the idempotency key, a GET on the out-edge key, and — on the insert path — a prefix scan of that source's segments. Then, after the loop, one GET per distinct (edge_type, src) to read the degree counter forward.

For a 1 024-edge batch across 1 024 distinct sources, that is roughly 3 000 sequential storage operations inside one transaction, inside the global write mutex. There is no get_batch, no join_all, no pipelining. If the average lookup costs 200 µs against a warm local cache, the batch costs 600 ms before the commit even starts, and no other write in the process can proceed during it.

03 — Findings

Write path, ranked

W1 · crit One mutex for every write in the process. acquire_local_write_guard takes the shard-wide local_write_guard and ignores its cell_id parameter, so the 64 writer_lanes above it are dead weight. Multi-tenant write throughput does not scale with cells, cores, or client concurrency. src/shard/lifecycle.rs:256 · src/core/state.rs:81 · src/shard/lifecycle.rs:187
W2 · crit A manifest refresh on every write attempt, inside that mutex. refresh_writer_fence takes writer_open_gate and calls writer.refresh_manifest(). It is a fencing check, and it is correct to make one — but making it per attempt rather than per interval puts a SlateDB manifest operation on the serialised critical path of every mutation. Retries re-pay it 32 times. src/core/state.rs:428 · src/shard/lifecycle.rs:264
W3 · crit No group commit. Each mutation commits its own transaction with await_durable. Because W1 serialises callers, concurrent writers cannot amortise a WAL flush between them — the classic fix (batch the queue behind the lock into one transaction) is unavailable while the lock is held for the whole read-modify-write. src/shard/write.rs:2934 · src/codec.rs:137
W4 · high Six to seven sequential reads before the first put. Idempotency, edge existence, segment scan, two vertex metadata reads, edge metadata, and one or two degree counters — each an independent key, each awaited in order. They are independent of one another and could be issued concurrently. src/shard/write.rs:2756–2901
W5 · high Batch writes are N serial single writes. No batched get, no concurrency across mutations, no reuse of the segment scan across the batch except a per-(type, src) memo built lazily inside the loop. src/shard/write.rs:4166–4324
W6 · fixed The dirty marker was re-written once per edge. It is now once per batch. mark_adjacency_dirty_txn has become mark_topology_change_txn, which takes the whole &[(VertexId, VertexId, bool)] change set and is called once per transaction rather than once per inserted edge — so the two fixed keys and the write.index_update span are paid once, not N times. The change-set parameter also feeds the xlog coverage floor the incremental builder relies on. src/shard/write.rs:5740
W7 · med Every write formats a token it never uses. LocalWriteGuard::new builds "{millis}-{pid}-{counter}" with a SystemTime::now() syscall, and renew()/release() are both Ok(()). Vestigial from an era when the guard was a distributed lease. src/core/state.rs:999–1015
W8 · med Keys are heap strings built with format!. A single batched edge insert allocates a fresh String for the idempotency key, the out-edge key, the in-edge key, both degree keys, and both dirty-marker keys — seven allocations plus integer formatting per edge, then as_bytes() to hand them to SlateDB. A SmallVec-backed byte-key builder would remove the allocation entirely. src/keys.rs
W9 · med Retry has no backoff. A serialisable conflict retries after tokio::task::yield_now() — 32 times, immediately, re-executing the full read chain each time. Under contention this converts one slow write into 32× the storage load. src/shard/write.rs:2567–2588

04 — Read path

What one query actually does

A four-rung dispatch ladder. Rung one is a compiled sparse kernel over an immutable CSC index and is genuinely fast. The fall-through is a full scan with an N+1 hydration loop — and the conditions that trigger the fall-through are more common than they look.

Figure 3 — execute_opencypher_rows, and where a query can fall off the fast path

The compiled path is good. The problem is everything that must be true for a query to stay on it, and the fact that the overlay work is redone from scratch every time.

The tail is the architecture's load-bearing shortcut, and its sharpest edge

Serving an index generation built at sequence N for a query pinned at M by replaying N+1..M from the WAL is what lets writes be visible without waiting for an index cycle. It is a good design, and its sharp edge has already been found and filed down once.

The edge was that the cost is request-bound, not data-bound: the delta is stored as one tiny WAL file per flush, so the price tracks the number of write flushes rather than the number of changed edges. A tenant trickling 200 edges over twenty minutes produces far more files — and therefore far more cost — than a bulk load writing 100k edges in ten seconds. That anatomy, measured on staging, is interactive/incremental-build-cost.html, and its fix ladder landed: parsed WAL files are cached by id, file fetches and per-edge resolution both run through buffered(...), and max_wal_tail_files declines a walk that would be too expensive rather than performing it.

What survives is smaller and worth stating precisely. Two queries arriving a millisecond apart against the same cell, edge type and read_epoch still resolve the same affected edges and build byte-identical overlays independently. The files are cached; the overlay is not. There is still no memo on (cell, edge_type, base_sequence, read_epoch), which is exactly the key that would make the second one free — and build_graph_index_incremental's own doc comment still says the read path computes this delta "and then throws away". That is R1b, and unlike the original R1 it deserves a measurement before a fix.

Every kernel read excludes the memtable

remote_read_options() pins durability_filter: DurabilityLevel::Remote, which SlateDB defines as "only data currently stored durably in object storage" — the default is Memory, which also serves the in-memory unflushed data. Block caching has since been made size-aware, but the durability filter has not. 

src/codec.rs:162
pub(crate) fn remote_read_options() -> ReadOptions {
    ReadOptions { durability_filter: DurabilityLevel::Remote, ..Default::default() }
}

pub(crate) fn remote_scan_options() -> ScanOptions {
    ScanOptions::default()
        .with_durability_filter(DurabilityLevel::Remote)
        .with_cache_blocks(false)
}

// added since: the right half of the original finding
pub(crate) fn remote_scan_options_for_expected_items(expected_items: usize) -> ScanOptions {
    ScanOptions::default()
        .with_durability_filter(DurabilityLevel::Remote)
        .with_cache_blocks(expected_items <= MAX_CACHED_REMOTE_SCAN_ITEMS)
}

The block-cache half is now handled the way it should be: a small repeated scan populates the cache, a large one-shot scan does not evict the working set, and the caller's own size estimate decides which it is. Call sites still using the unconditional remote_scan_options() are worth auditing individually, but the mechanism exists.

The durability filter is untouched, and it is the larger of the two. Remote is presumably deliberate — it keeps snapshot semantics honest against a fenced writer — but it means a read-your-write workload pays object-store-cache latency for data written microseconds ago, on every kernel read. That is still the single highest-leverage measurement in the plan: flip it in a branch build and diff the flamegraph (B4). If the delta is large, the correctness argument deserves re-examining per call site rather than being applied globally — and if it is small, this finding should be struck.

05 — Findings

Read path, ranked

R1 · fixed The WAL-tail walk was serial, uncached and unbounded. All three are now addressed. This was the headline read-path finding and it is no longer accurate. Current topology_tail_since carries a WalTailFileCache of parsed WAL files keyed by WAL id — a WAL id names an immutable object, so a cached parse never goes stale and eviction exists only to bound memory. File fetches and per-edge resolution both run through buffered(wal_tail_fetch_concurrency()) instead of a serial loop, and a max_wal_tail_files gate declines the walk rather than grinding through it. The reasoning is interactive/incremental-build-cost.html; the shape of the fix is that note's L0–L3 ladder. src/shard/topology_tail.rs:219–360
R1b · med What remains: the overlay itself is still per-query. The files are cached and the fetches are parallel, but the resulting GraphTopologyOverlay is not memoised. Two queries against the same (cell, edge_type, base_sequence, read_epoch) still resolve the same affected edges independently — cheaper than before, and still duplicated work on a key that is exactly available. Much smaller than the original finding; worth a measurement before a fix. src/shard/topology_tail.rs:335–359
R2 · crit Any concurrent write knocks a query off the compiled path. compiled_graphblas_query_snapshot pins a fresh snapshot and returns Ok(None) if snapshot.seq() != read_epoch. Under a mixed read/write workload this fires constantly, and the fall-through is the rung-5 full scan. The counter that would show it — graph_query_rust_sparse_fallbacks — exists; nothing charts it. src/shard/query.rs:5556 · src/shard/topology_tail.rs:90
R3 · high snapshot_at hard-errors unless the epoch is exactly current. The batch neighbour APIs read current_epoch and then call snapshot_at with it; a write landing in between turns the query into an UnsupportedQuery error rather than a slightly-stale read. Availability degrades with write rate. src/shard/lifecycle.rs:706–733 · src/shard/query.rs:5703
R4 · high Frontier expansion is serial, one source at a time. out_neighbors_batch_at_with_cancellation and reachable_from_storage_frontier both loop for source in frontier { …await… }. Each source costs three prefix scans (edges, segment tombstones, segments). A 1 000-node frontier is 3 000 sequential scans where the snapshot is immutable and they could all run concurrently. src/shard/query.rs:5751 · src/shard/query.rs:5143 · src/shard/query.rs:130
R5 · partly fixed Block caching is now size-aware; the durability filter is not. remote_scan_options_for_expected_items enables cache_blocks when a scan expects at most MAX_CACHED_REMOTE_SCAN_ITEMS, so small repeated scans populate the cache and only large one-shot scans bypass it — which was the right half of the original finding. Unchanged: every kernel read still sets DurabilityLevel::Remote, which SlateDB defines as excluding in-memory unflushed data. A read-your-write workload still pays object-store-cache latency for data written microseconds ago. R6 · high One heap String allocated per key, per scanned row. Every scan loop in the codebase does String::from_utf8_lossy(&kv.key).into_owned() before parsing — including the hot ones. On a million-edge scan that is a million allocations whose only purpose is to hold a key that is already valid UTF-8 in a borrowed buffer. std::str::from_utf8(&kv.key) borrows instead, as collect_topology_entry already does. src/shard/query.rs:116,147,158,177 · src/codec.rs:23,83,103 · src/engine/artifact_build.rs:606
R7 · high Parameterised queries never hit the plan cache. parsed_opencypher_row_query returns early whenever parameters is non-empty, so every query from a Neo4j driver — which parameterises by default — re-runs libcypher-parser and the full lowering on every execution. Splitting parse (parameter-independent) from parameter substitution would make the cache serve the workload it was built for. src/shard/query.rs:501
R8 · high The bounded cache is an O(n) LRU behind an exclusive async mutex. BoundedGraphCache::get takes &mut self, so even a hit needs the exclusive tokio::sync::Mutex; evict_one linearly scans the whole BTreeMap for the minimum last_access and runs in a while loop until under budget; get_latest_by — the artifact lookup on every compiled query — scans every entry. Every query serialises on these. src/core/cache.rs:241,355,248 · src/engine/artifact_build.rs:564
R9 · med Cache keys allocate two Strings per lookup. MatrixCacheKey::new(cell_id, edge_type, epoch) and its four siblings to_string() both components on construction — including on the read-only probe path, before it is known whether an insert will happen. src/core/cache.rs:11–117
R10 · med A generation-map miss becomes an object-store GET on the query path. graph_index_generation_at → discover_graph_index → current_graph_index does an unconditional object_store().get(current_ptr). There is no negative cache and no TTL, so a cold or evicted entry costs a full round trip mid-query, twice in the refresh-retry branch. src/engine/index_store.rs:64,85,388
R11 · med The rung-5 row engine is a textbook N+1. match_edge_row_pattern_full_scan materialises every edge of the type, then per edge calls push_matching_edge_row, which does a relationship lookup plus two metadata hydrations — each an awaited storage read, memoised only within the one query. src/shard/query.rs:3599–3694
R12 · med LIMIT is applied after everything is built and sorted. finish_projected_rows dedupes, sorts, and only then skips and truncates. MATCH … RETURN … LIMIT 10 over a million matches builds and sorts a million rows. R13 · med Overlay deletions are quadratic in the frontier. In expand_range_with_overlay, removing a destination runs frontier.iter().any(…) with a compiled_graphblas_contains_edge probe inside, per changed destination per hop. Delete-heavy workloads with wide frontiers pay |frontier| × |changes| kernel probes. src/shard/topology_tail.rs:217–239

06 — Cross-cutting

Three things that are true of both paths

Async, but not concurrent

Both paths are written as async fn and both are effectively sequential. Every fan-out — batch mutations, frontier expansion, tail edge resolution, batch existence checks — is a for loop with an .await in the body.

The pinned snapshot makes these trivially parallelisable: reads against GraphStorageSnapshot are immutable and independent. A bounded buffer_unordered over the same work would turn latency-bound loops into throughput-bound ones without touching semantics.

Allocation per unit of work

A String per key built, a String per key parsed, two Strings per cache probe, a token string per write, a BTreeSet/BTreeMap per intermediate collection. None of it is wrong; all of it is on the hot path.

These are the allocations a flamegraph will surface as a wide malloc / memcpy band underneath otherwise-sensible frames. Fix them after the structural items, not before — they are 10–30% wins under a 10× problem.

Silent demotion

Six distinct conditions turn a compiled traversal into a full scan, and all six return Ok(None). The query still succeeds; it just costs a hundred times more. From the outside this looks like unexplained p99 variance.

The instrumentation to see it already exists — artifact.lookup records turbolay.outcome, storage.wal_tail records complete/unavailable, and graph_query_rust_sparse_fallbacks counts the demotions. Panel 4 of the dashboard below is that signal.

What is genuinely good

The metrics layer: 65 lock-free relaxed counters plus fixed-bucket histograms designed specifically to avoid the OTel RwLock + HashMap + per-attribute Mutex on the query path (src/core/histogram.rs:1). The span tree — shard.write_txn, storage.commit, artifact.lookup, storage.wal_tail, kernel.expand — is already shaped for exactly this investigation, including counting spawn_blocking queue time separately from compute.

This means the dashboard in §09 is a config exercise, not an instrumentation project.

07 — Benchmarks

Turning each claim into a number

Every finding above is a hypothesis with a predicted shape. A benchmark is only worth running if a specific finding predicts what it will show.

Four harnesses already exist and cover more ground than a new one would: examples/write_profile.rs (ingest, batched and trusted-append, with the bulk-import stage counters wired up), examples/query_bench.rs (cold/hot/ concurrent, parameterised by fan-out and hop count), examples/batch_benchmark.rs, and examples/incremental_index_bench.rs. Run them through just, not bare cargo — the FFI env vars are exported there.

08 — Flamegraphs

Four profiles, not one

A single mixed profile will show a flat, uninformative spread. Profile each path in isolation, and profile the off-CPU time separately — most of these findings are waiting, not computing.

Add a [profile.profiling] section inheriting release with debug = 1 and strip = false so symbols survive; the existing release profile is what production runs, and the frame names are what makes a flamegraph readable. 

Cargo.toml
[profile.profiling]
inherits = "release"
debug = 1
strip = false
split-debuginfo = "packed"
#ProfileToolTargetLook for
F1 On-CPU, write cargo-flamegraph / perf write_profile, batch 1024, saturated Width of format!/alloc under keys::* (W8); refresh_manifest (W2); encode/decode vs actual SlateDB work.
F2 Off-CPU, write tokio-console, or offcputime/perf sched same workload Time parked on local_write_guard. This is the W1 proof: an off-CPU flamegraph dominated by one mutex is unambiguous in a way a CPU profile is not.
F3 On-CPU, read (compiled) cargo-flamegraph query_bench hot, index fresh Split between SuiteSparse frames and everything around them. If the GraphBLAS band is thin, the kernel is not the cost — the plumbing is.
F4 On-CPU, read (lagging index) cargo-flamegraph query_bench after B5's 100k-edge lag A topology_tail_since tower with edge_exists_in_storage_snapshot underneath it, plus from_utf8_lossy/into_owned (R6). Diffing F3 against F4 is the cost of R1.
F5 Differential flamegraph.pl --negate B4's two builds Exactly what changes when the durability filter and block caching change. A differential graph answers B4 in one image.
F6 Allocation heaptrack / dhat read and write, one run each Allocation count per edge processed. Ties W8, R6, and R9 to one number that is easy to track as a regression gate.

On macOS perf is unavailable and samply or Instruments is the substitute; on Linux prefer perf record -F 997 --call-graph dwarf. Because the traversal runs on spawn_blocking, make sure the profiler samples all threads — the kernel.expand span already tells you how much of that duration was queueing rather than working, so cross-check the two.

Add to the justfile just flame-write · just flame-query · just flame-query-lagging — each exporting the same FFI env vars the other recipes do, writing SVGs to target/flamegraphs/<name>-<git-sha>.svg. Naming by SHA is what makes the before/after comparison possible three weeks later.

09 — Grafana

The dashboard, panel by panel

The node already exposes /metrics and the chart already ships a ServiceMonitor. Everything below uses series that exist today; the two gaps are flagged as such.

Five histogram families are exported with real buckets — graph_client_operation_read_duration_seconds, graph_client_operation_write_duration_seconds, graph_query_rows_duration_microseconds, and the two transport families — so histogram_quantile works. Everything else is a monotone counter, which means stage timings come out as means (rate(sum)/rate(count)), not quantiles. That is a real limitation and the runbook docs/runbooks/duration-histograms.md already says the buckets carry 20–30% quantile error by design. Chart accordingly: these panels answer "did it move 2×", not "did p99 move 5 ms".

Bulk import stage split rate(graph_bulk_import_{preflight,batch_build,counter_read,commit}_microseconds[5m]) / rate(graph_bulk_import_batches_profiled[5m]) Four series stacked: mean µs per batch by stage. If counter_read and preflight dwarf commit, W4/W5 are confirmed in production, not just in a bench.

Row 3 — Read path and the fast/slow split R1 R2

PanelQueryReads on
Compiled-path demotion rate key rate(graph_query_rust_sparse_fallbacks[5m]) / rate(graph_query_rows_started[5m]) The fraction of queries that fell off the compiled kernel. This is the most diagnostic single number on the board and nothing charts it today. Alert if it crosses ~0.05 sustained.
Artifact vs rebuilt snapshots rate(graph_query_graphblas_artifact_snapshots[5m]) vs rate(graph_query_graphblas_rebuilt_snapshots[5m]) Rebuilds are the expensive branch. A rising rebuild share means the indexer is not keeping up (R1).

Kernel queue vs compute rate(graph_compute_queue_microseconds[5m]) / rate(graph_compute_duration_microseconds[5m]) Ratio above ~0.3 means spawn_blocking is the bottleneck, not the traversal. The kernel.expand span was built for exactly this question.
Rows returned per query rate(graph_query_rows_returned[5m]) / rate(graph_query_rows_completed[5m]) Latency that rises while this stays flat means the extra cost is not result size — it is the tail (R1) or the demotion (R2).

The two gaps

Gap 1 Index lag is not a metric. The board can show that builds are happening, but not how far behind the current generation is — read_epoch − generation.base_sequence, which is precisely the quantity R1 says read latency is proportional to. Both numbers already exist on the artifact.lookup and storage.wal_tail spans (turbolay.read_epoch, turbolay.base_sequence). Exporting the difference as one gauge per (cell, edge_type) would make the most important curve in §07 continuously observable.
Gap 2 Lock wait is not a metric. There is no counter for time spent parked on local_write_guard. graph_backpressure_waits covers the semaphore gates but not the mutex, and the mutex is the one that matters (W1). A single write_lock_wait_us counter alongside the existing write counters would turn W1 from an argument into a graph — and would prove the fix worked.
Provisioning Ship the board as JSON under charts/turbolay/ beside the existing servicemonitor.yaml, templated into a grafana_dashboard-labelled ConfigMap so the sidecar picks it up. That keeps the dashboard versioned with the metric names it depends on — a rename in admin.rs's PROMETHEUS_COUNTERS table and the panel that breaks then move in one commit.

10 — Sequence

What to do in what order

First Measure, do not fix. Land the dashboard, the two missing metrics, and the flamegraph recipes. Run B1, B5, and B6. Those three curves either confirm W1, R1b, and R2 or send this note back for revision — which is exactly what happened to the original R1, and is the point of running them.
Then The one structural item left. Make local_write_guard per-cell — it already takes the cell id — and move the fence refresh off the per-attempt path onto an interval, so W1 and W2 stop being the write ceiling. The read-path twin of this has already been done: the WAL-tail ladder landed and R1 is closed. Nothing else on the list changes the shape of the write curve; this does.
Then Concurrency in the fan-outs. W4, W5, R4 — bounded buffer_unordered over work that is already independent against a pinned snapshot. Mechanical, individually verifiable, and each one is a separate PR with its own before/after flamegraph.
Then The plan cache and the cache implementation. R7 (split parse from parameter binding) and R8 (a sharded, non-exclusive cache with O(1) eviction). Both are contained changes with a clear metric to prove them: the parsed-row-query hit ratio, and the concurrency plateau in B9.
Last Allocation and micro-cost. W7, W8, R6, R9 — worth doing, worth doing after the above, and worth gating with the heaptrack number from F6 so they do not silently regress.

Two caveats worth stating plainly. First, DurabilityLevel::Remote and snapshot_at's exact-epoch requirement (R3, R5) look like performance bugs and may well be deliberate correctness decisions whose reasoning is not written down where this reading found it. B4 and B6 are designed to price them, not to presume them wrong; if the price is high, the question is whether the guarantee must hold at every call site or only at some.

Second, and more usefully: this note has already been wrong once. Its original headline read-path finding described a serial, uncached, unbounded WAL-tail walk, and by the time it was re-checked that had been measured, documented and fixed by someone else. A static reading of a moving tree has a shelf life. Re-verify before acting, and treat the file:line references as the thing to check rather than the thing to trust.
