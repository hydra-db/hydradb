Requests, Not Bytes

Why loading a 100 k-edge delta got slower than scanning the whole 1 M-edge graph — a cost anatomy of the incremental index build, measured on staging, and the design that restores the bet.

2026-08-05 · staging incident analysis · companion to docs/benchmarks/2026-08-03-incremental-index-build.md · code refs at src/shard/topology_tail.rs:75, src/engine/index_store.rs

1The bet, and the assumption smuggled inside it

The incremental build banks on one inequality: the change set is always far smaller than the graph. A million-edge graph gets a hundred thousand new edges in a busy half hour; touching 100 k things must beat touching 1 M things. The bet is correct — as a statement about work per item. The 5 M-edge benchmark proved the apply-and-re-encode side handily: 26× faster than a full rebuild.

The smuggled assumption is in the word loading. It reads as “cost ∝ items”. But nothing in a storage system charges you per item. You are charged per request, and a request costs the same ~50 ms against S3 whether it returns one useful edge or forty thousand. So the real inequality that decides the winner is:

items ÷ items-per-request is what you pay — not items. The full scan gets its 1 M edges at ~40 k useful edges per request. The tail walk gets its delta at ~0.01 useful edges per request. That is a six-orders-of-magnitude per-item handicap, and it flips the bet.

2Where each copy of the truth lives

The same edges exist in three shapes, and the shapes — not the counts — set the price.

Three consequences fall out of Shape B being the delta source:

The delta is never stored as “100 k edges you can load.” It is stored as N tiny files where N counts write flushes, not edges. A tenant trickling 200 edges over 20 minutes produces ~2,000 files; a bulk load writing 100 k edges in 10 seconds produces ~100. Same delta size, 20× different price. Write pattern, not write volume, sets the cost.

The walk is serial. topology_tail.rs:75 awaits each file before requesting the next: span × RTT wall-clock, no overlap.

The walk repeats. All 8 edge types share one database, the per-edge-type filter runs after download, and nothing remembers the walk between builds. The same file is downloaded by the reader's replay, then up to 8 more times by builds — 9 purchases of the same bytes, 8 discarded.

4The request arithmetic, priced

A reasonable first analogy: “both paths hit S3; the full path just makes ~10× fewer GET calls and takes ~100× more data per call.” The direction is right; the magnitude is not even close — and the gap is not one number but three multiplied together: request count × useful payload × amortization.

So it is not “10× fewer calls at 100× the data.” It is tens of amortized calls at ~10 ⁴ useful edges each, versus thousands of unamortized calls at ~10 ⁻² useful edges each — a per-edge price gap of six to eight orders of magnitude.

And the “worst case that will never happen” happened — and was undershot. The intuitive worst case is one request per delta edge (a tenant trickling one edge per ~100 ms flush: 100 k edges → 100 k files → 100 k GETs). Staging measured worse than one request per edge, routinely: builds paid 2,000 requests to recover 15-edge deltas — 0.0075 useful edges per request. Two reasons: WAL files interleave all 8 edge types plus vertex/property writes, so most files contain zero entries for the edge type being built; and each of the 8 edge types re-walks the same files, dividing the useful yield again. The sub-worst case is the common case.

5Two feedback loops made it worse every day

Loop 1 — staleness compounds. Slow builds stretch the indexer cycle (7 min → 15–40 min). A longer cycle means more WAL accumulates before the next visit, which means a longer walk, which stretches the cycle further. Average build: 27 s on Aug 4, 48 s on Aug 5.

Loop 2 — the fleet grew under it. Registered scopes went from ~110 to ~300 in four days, and the cycle visits every scope serially at 3–4 s each (open reader, establish checkpoint via manifest CAS, check dirty, close, delete checkpoint) — ~20 minutes of fixed overhead per cycle before any build runs. Not caused by the incremental change, but it multiplies Loop 1 by delaying every revisit.

The design hole in one sentence: the builder declines the incremental path when the delta is unavailable (a WAL file was garbage-collected) but never when it is merely ruinously expensive — it has a correctness gate and no cost gate, so it grinds through 10,000 round-trips to discover 15 edges rather than falling back to a 1-second scan.

6Why the read path never noticed

The obvious objection: queries use the same tail walk (shard/query.rs:5525 calls the very same topology_tail_since) to overlay freshness onto a compiled matrix. If the walk is ruinous, reads should have been screaming for months. They weren't — and the reason is the design lesson of this whole incident, so it deserves its own anatomy.

First, the objection's premise is right about one thing: everyone loads data eventually. A cold read pays the manifest, the bounded replay, and SST block fetches — the same cold-open tens-of-requests the full build pays. The difference is which shape each consumer depends on. Every read route terminates in Shape A — bulk, packed, cached, amortized. No read route requires Shape B. Reads sample the shredded history opportunistically, and every gate on the way out fails toward Shape A:

gate on the matrix + overlay routewhereon failure
1 · Sparse-kernel policy is Adjacency — compiled route disabled wholesalematrix_cache.rs:52 snapshot scan (Shape A)
2 · No compiled matrix cached or hydratable for the current generation query.rs:5492snapshot scan (Shape A)
3 · Generation already covers the read epoch — the common case when the indexer keeps uptopology_tail.rs:65 empty overlay, zero walk
4 · Walk under way but a file is missing (GC) or the query deadline (QueryBudget, checked per file) fires topology_tail.rs:76,85 abort mid-walk → snapshot scan (Shape A)

So the read path and the incremental builder are not “the same code, different luck.” They are the same walk under opposite contracts: for a read the walk is an optional accelerator with an abort lever and a cheap, always-correct fallback standing behind it; for the builder it was the primary data source with no abort lever for cost — only for correctness. The builder was the only caller in the system required to finish the walk.

Staging evidence that the gates, not luck, did the work: 16,500 query.execute spans over three days averaging 118 ms with p99 2.5 s, and zero storage.wal_tail spans from the nodes in seven days — the span is tail-sampled away unless it errors, and none errored. Which is also the uncomfortable part: reads were silently fine. If they had been quietly aborting expensive walks every query, the telemetry would look identical. That observability hole is a first-class deliverable of the fix (§8), not a footnote.

The transferable lesson: any consumer of Shape B must either hold a stateful position in it (the reader's replay marker) or hold an exit to Shape A priced in advance (the read path's gates). The incremental builder shipped with neither — it held a stateless position and an exit that only opened on missing data, never on cost.

8The fix: make delta derivation obey the bet

The invariant to enforce, mechanically: the incremental path must never cost more than the full path — it estimates its derivation cost up front and forfeits when it would lose. Then, separately, shrink the derivation cost until forfeits are rare.

L0Cost gate — the missing decline

The builder already knows the span for free: durable_wal_id − generation.last_wal_id. If span × RTTest > full-scanest, decline → full build → re-base. Extends the existing decline-not-guess design from correctness to cost; restores the invariant by construction, with everything else purely improving the win rate.

Lands at the top of the incremental branch in index_store.rs, before any S3 work:

let span = durable_wal_id.saturating_sub(previous.last_wal_id);
if span > max_tail_files {          // v1: static knob,
    return self.build_full(..,       // GRAPH_INDEXER_MAX_TAIL_FILES
        DeclineReason::TailTooExpensive).await;
}

The decline increments the existing fallback counter with a new reason label, so the dashboard separates “chain broken” from “chain too long” — today's 98-fallback panel can't tell them apart.

size: small · one PR with L1 · new decline reason on the fallback counter

L1One walk, shared and concurrent

Walk the span once per scope-cell per cycle, collecting affected keys for all 8 edge types in a single pass (the per-type filter is a per-key string match — trivially widened), fetching 16–32 files concurrently. Turns 8 × 100 s into ~6 s for a 2,000-file span: a ~130× wall-clock win that changes no interface. The class stays O(write activity) — L0 remains the backstop.

Mechanically: a sibling of topology_tail_since in topology_tail.rs returning BTreeMap<EdgeType, GraphTopologyOverlay>; collect_topology_entry already parses the edge type out of the key, so the filter widens from == edge_type to ∈ registered set. Fetches go through futures::stream::iter(ids).map(get).buffer_unordered(N); per-file iterators drain as they arrive; the per-entry sequence guards (seq ≤ base, seq > read) are unchanged — note the base sequence differs per edge type's generation, so the shared walk keeps entries down to the oldest base among dirty types and each type's overlay applies its own guard. One subtlety: a missing file now declines all edge types sharing the walk — which is the same outcome they'd each reach alone.

size: small-medium · same PR as L0

L2Capture history where it already flows

The reader's replay downloads every WAL file exactly once, at exactly the right moment — then discards the history. Tee it instead: during replay, append topology change events (edge_type, src, dst, seq) to a small per-scope changelog the builder keeps. Delta derivation becomes a RAM lookup — zero additional S3, cost ∝ delta size, the bet honored by construction.

Shape of the hook, on our SlateDB fork (we own the pin):

// fork: DbReaderOptions grows an observer the replay loop invokes
pub trait WalReplayObserver: Send + Sync {
    fn entry(&self, wal_id: u64, key: &[u8], value: &ValueDeletable, seq: u64);
}
// kernel: observer feeds a per-scope ring keyed by seq, recording
// (edge_type, src, dst) via the same parser as collect_topology_entry.
// Builder asks: changelog.entries_since(base_seq)
//   → Some(delta)  if base_seq ≥ changelog.low_water  → apply, done, 0 GETs
//   → None         otherwise                          → L0 decline → full build

The changelog knows its own coverage (low_water = the seq where its history begins), so correctness is a range check, not a hope. Memory is bounded by ring size; overflow just raises low_water — degrading to a decline, never to a wrong answer. The remaining requirement is that the changelog outlive the visit, which points at keeping hot scopes open across cycles (LRU) — the same lifecycle change that dissolves Loop 2's 20 minutes of open/close churn. After restart or eviction: L0 declines once, re-bases, resumes. Same self-healing shape as the GC fallback.

size: medium, own design round · fixes both fires with one lifecycle change

L3Delta-shaped generations

The builder publishes deltas alongside periodic full generations; readers compose. No consumer depends on WAL retention or replay at all. The endgame — already the phase-2 plan — and unblocked, not replaced, by L0–L2.

size: large · phase 2

9Landed: L0 + L1, measured on real S3

Branch feat/wal-tail-cost-gate implements the first two rungs (commit 80b922d): the cost gate (GraphLimits::max_wal_tail_files, default 4096, GRAPH_INDEXER_MAX_TAIL_FILES in the indexer), the 16-way concurrent fetch (GRAPH_WAL_TAIL_FETCH_CONCURRENCY; 1 reproduces the old serial walk), and the per-shard parsed-file cache (WalTailFileCache) that lets the 8 edge types share one span's downloads. Declines log their reason at info. Two new regression tests pin the behavior: a span over the cap declines to a correct full rebuild, and the second edge type's walk downloads nothing.

Measured against real AWS S3 (bucket hydradb-local-turbolay, us-east-1) with examples/wal_tail_trickle_bench.rs, which manufactures the staging shape: 100 k seeded edges per type, then 500 single-edge commits per type — each its own WAL flush — before one build walks the span.

Two honest caveats and one controlled number. The client ran far from us-east-1 (~300–800 ms per request — an in-cluster indexer sees 1–5 ms), so the absolute times above are inflated ~100×; the ratios and outcomes are what transfer. And because remote absolute numbers are junk for regression tracking, examples/tail_concurrency_probe.rs re-measures the walk under a deterministic injected latency (ThrottledStore, 25 ms/GET, 100-file span): 16.8 s serial vs 4.7 s fixed — the walk itself parallelizes ~16×, and the remaining serial cost is SlateDB's own WAL replay inside reader refresh, which only the L2 work can remove.

A finding the benchmark threw in for free: re-opening the shard over the freshly trickled span stalls in SlateDB's own WAL replay — the open performs the same serial file-by-file walk before the database is usable. The indexer's per-cycle open/close of every scope pays this too, which is more evidence for the keep-scopes-open LRU in L2: replay cost should be paid incrementally by a long-lived reader, not repeatedly by fresh opens.

10Open questions for discussion

Preserved as written 2026-08-05; §11 records how each resolved.

Where does the changelog live? In the builder (fork exposes a replay callback; kernel stays generic) or inside the fork's reader itself (reusable by the read path's overlay too — which today re-derives the same tail per query and survives only by falling back)? The second is more invasive but pays twice.

Keep-open LRU sizing. ~300 scopes and growing; a reader holds memory + a checkpoint. What's the residency budget — and should dirtiness (cheap S3 list) gate visiting at all, so quiet scopes cost nothing?

L0's estimator. Static file-count threshold (simple, one knob) vs measured EWMA of per-file RTT and per-edge scan rate (self-tuning, more moving parts)?

Observability debt. A build_duration_seconds histogram labeled by path, a counter for declined-for-cost, and keeping (not sampling away) the read path's declined-tail spans — this failure mode was invisible by construction; the next one shouldn't be.

11Landed: the changelog moved to commit time — the xlog

Shipped 2026-08-07 on feat/xlog-incremental-index (PR #25, ticket PRO-1469; full design and verification in docs/plans/2026-08-05-edge-changelog-incremental-index.md). §10's first question — where does the changelog live, the builder or the reader? — got a third answer that beats both: the write path itself. Every topology mutation writes one entry per changed edge, in its own transaction:

cell/{cell}/xlog/{edge_type}/{seq:020}/{src:020}/{dst:020}  →  0x01 exists / 0x00 deleted

Because the sequence and the edge are in the key, nothing overwrites; because seq/src/dst sort lexicographically, one edge type's changes are one contiguous run; and because the value is final state (last-in-sequence wins per (src, dst)), overlay application is idempotent and crash-replay of an overlapping range is harmless. The entries ride the same WriteBatch → WAL object → memtable → SST pipeline the mutation already pays for — zero new files, zero new requests, ~72 bytes per change — and compaction folds them into the same fat SSTs the full scan reads. The delta ends up stored in Shape A: derivation is one bounded range scan, O(delta) bytes, independent of WAL file count, write cadence, and elapsed time.

Why commit-time beats the §8-L2 replay-time hook it replaces: the changelog is durable data, not process RAM — it survives restarts, needs no keep-scopes-open LRU to outlive a visit, is already per edge type, and its sequence stamp is the pinned commit sequence the engine either honors exactly or rejects (InvalidSequenceNumber), so stamp order provably equals visibility order. Coverage is a range check against a low-water floor (meta/xlog_low), maintained by the writer and advanced by a writer-gated GC pass; a breach is a one-time bootstrap full build, never a wrong answer — the same decline-not-guess shape as everything else, minus the cost gate, because there is no cost to gate: the builder never walks WAL at all, so §8's L0 estimator question is moot and max_wal_tail_files is now a read-path-only knob. The compiler enforces capture coverage: mark_adjacency_dirty_txn became mark_topology_change_txn(…, changes), all 11 mutation sites converted, old signature deleted — a future site that marks dirty without declaring its delta fails to compile, and a randomized property test (xlog_incremental_matches_full_over_random_mutation_mix) asserts payload-hash equality with a full rebuild after every mutation burst.

The staging replay. examples/staging_replay_bench.rs recreates the operating loop that actually degraded — 8 edge types in one scope DB, an indexer cycle per round, ~215 hot-type commits and exactly 15 edges per quiet type per cycle — so every quiet build faces §3's exact signature: a 15-edge delta under a ~330-file span it had no part in creating. Result over four cycles: quiet-type builds of 17–28 ms (the old walk's measured cost for the same shape is ~16 s — ~850×), the full 8-type cycle in ~0.6 s against staging's regressed 15–40 minutes, one planned bootstrap cycle then zero fallbacks, exact delta counts throughout, and a per-cycle full-rebuild equivalence probe agreeing every time.

Every run reported the exact trickled delta count with zero fallbacks. Compare §9: on this same bucket the serial walk could not finish a ~1,000-file span in 10 minutes and the gated 16-way walk took 478 s — the xlog build is indifferent to the span entirely, including spans WAL GC has already collected, the failure that §9's last row could only survive by declining. The residual real-S3 incremental seconds are the shared reader-refresh replay both paths pay once per database per refresh; the in-memory 2 M row shows the CPU-side win (no per-edge string parsing) that remains after all request latency is subtracted. What is deliberately not claimed: the CSC re-encode and payload PUT are still O(graph) — §8's L3 (delta-shaped generations, now "Phase 2" in the plan doc) is unchanged, unblocked, and fed directly by the xlog scan's output.

Of §10's remaining questions: the keep-open LRU stays worthwhile purely for Loop 2's open/close churn (the xlog no longer needs it for correctness); the estimator question dissolved with the gate; the observability items stand and now include the artifact.xlog_gc span the indexer's cleanup step emits.
