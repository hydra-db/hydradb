Rendezvous hashingevery machine computes the same owner, from nothing but the question itself

Also called highest random weight, or HRW. It answers one question — which machine handles this item — and it answers it identically on every machine, with no coordinator, no stored table, and no messages. This page explains what it is, why the property that makes it valuable is the one you should care about, and where it is the wrong tool.

A — the question

Several machines, many items, and nobody in charge

Every problem rendezvous hashing solves has the same shape. Fix that shape first; the mechanism takes one line once you have it.

You have a set of machines — processes, servers, pods, it does not matter which — and a much larger set of items. An item is anything that needs exactly one machine responsible for it: a cache key, a shard, a partition, a database whose writes must be serialised. Each machine must be able to answer which machine handles this item? and every machine must give the same answer.

The constraints are what make this interesting. There is no coordinator to ask. There is no election. There is no shared database holding the assignment, and the machines do not send each other messages to agree. Each one works it out alone, from what it already knows, and they still agree.

term — coordinator

A separate service that owns the assignment and hands it out — ZooKeeper, etcd, a placement driver, a leader-elected controller. It works, and it is frequently the right answer. It is also a service you now run: another process to deploy and upgrade, another thing that has to fail over, another quorum to keep healthy, and another source of truth that can disagree with the one you already had. Every lookup either crosses the network to it or reads a cache of it that can be stale.

Avoiding the coordinator is not about elegance. It is about not adding a distributed system to the inside of your distributed system. If the answer can be computed from inputs both sides already hold, no agreement protocol is required, because there is nothing to agree about.

what we want owner(item) — a pure function of the item and the current machine list.
Same inputs, same output, on every machine, with no communication.

Two inputs, then. The item, which the caller has. And the list of live machines, which every machine can obtain some other way — from configuration, from a service registry, from a directory of heartbeat records. Getting that list consistent is a real problem and it is not the problem on this page. Assume it for now.

B — the obvious answer

hash(item) % N, and the reason it does not survive contact

The first idea anyone has is the right first idea. Hash the item to a number, take that number modulo the machine count, and use the result as an index into the machine list.

term — hash function

A function turning a string of bytes into a fixed-size number, such that similar inputs give unrelated outputs and the outputs are spread evenly across the range. No cryptography is needed here — nobody is attacking the placement — so this page, like the repo, uses FNV-1a 64: a five-line loop of xor and multiply producing a 64-bit value. 

index = fnv1a64(item) % N
owner = machines[index]

It is fast, it needs no state, and it distributes evenly. It is also correct only while N never changes, and N is the machine count, so it changes every time a machine is added, removed, restarted, or declared dead.

The damage is worse than intuition suggests. Going from three machines to four, you might hope a quarter of the items move — the new machine's fair share. What actually happens is that an item keeps its owner only when h % 3 == h % 4, which holds for 3 of every 12 residues. Three quarters of all items relocate. Nothing about the surviving machines changed, and yet almost everything moved.

Relocation is not free. Depending on the system, a moved item means a cache miss, a re-replicated shard, a rebuilt index, or a database reopened by a different writer. Moving 75% of the fleet's items because one machine joined is disqualifying on its own.

C — the idea

Score every pair, take the highest

One sentence, and it is the whole mechanism.

rendezvous hashing owner(item) = the machine m maximising H(item ‖ m), over the live machines.

The inversion is the point. Modulo hashes the item and then maps the result onto a machine, so the mapping depends on how many machines there are. Rendezvous hashes the pair: it computes a score for this item against machine A, another against machine B, another against machine C, sorts those scores descending, and takes the top. The item's own hash is never mapped anywhere, so the machine count never enters the calculation.

The name comes from that: the item and its machine meet at the highest score, and both sides can find the meeting point independently. "Highest random weight" describes the same thing from the other end — each machine is assigned a pseudorandom weight for this particular item, and the highest weight wins.

Count the machinery. There is no ring. There are no virtual nodes. There is no stored assignment, no table to replicate, no invalidation, no bootstrap, no migration procedure for the mapping itself. The score is recomputed from scratch on every lookup, and the answer is the same on every machine because it is a pure function of two things both already have. State that cannot exist cannot be stale.

Ties need one rule, or two machines could each believe they won. Break them by machine identifier ascending — a total order every machine can evaluate locally. With 64-bit scores a tie is vanishingly rare, which is exactly why it must be handled: a bug that fires once a year is worse than one that fires daily.

What this page actually computes

Every score below is a real FNV-1a 64 hash, evaluated in your browser with BigInt, using the same key layout the repo froze in crates/placement/src/hash.rs: 

score(scope, cell, node) = fnv1a64(scope ‖ 0x00 ‖ cell_id ‖ 0x00 ‖ node_id)
rank                     = descending by score, ties broken by node_id ascending
owner                    = rank[0], or none when no machine is live

The vocabulary maps directly: a cell is the item, a node is the machine, and scope is a namespace prefix that keeps two graphs from sharing a placement. The 0x00 bytes are separators, and they are load-bearing: without them ("ab", "c") and ("a", "bc") would produce identical keys and two different items could share an owner by accident.

D — the property that matters

Remove a machine and only its own items move

This is the reason to use rendezvous hashing. Everything else about it is convenience.

Kill one machine out of six. Its items have to go somewhere — that is unavoidable, their owner is gone. What is not obvious is that nothing else moves at all. Not approximately nothing; exactly nothing. Every item owned by a surviving machine is still owned by the same surviving machine.

The reason is worth understanding rather than memorising, because it tells you when the property holds and when it does not.

Each machine's score for an item is computed from the item and that machine alone. Machine C's score does not read machine B's identifier, or the machine count, or the position of anything in a list. So deleting machine B from the live set cannot change any other machine's score by even one bit. The scores are the same numbers they were before; the only difference is that one of them is no longer in the running.

Take a sorted list of unchanged numbers and delete one entry. Everything above the deleted entry keeps its position. Everything below moves up exactly one place. So an item whose winner is still alive still has the same winner — its top score was not the one removed. An item whose winner is gone gets the machine that was already in second place. No other item is affected, and no third machine ever learns that anything happened.

the intuition in one line Scores are independent, so removing a machine deletes one row from a sorted list
and reorders nothing. Second place becomes first. That is the entire disturbance.

Adding a machine is the mirror image. The newcomer computes a score for every item and wins the ones where that score happens to be the highest — roughly a 1/N share — and loses every other item to whoever already held it. Both directions move the theoretical minimum number of items, which is what minimal disruption means.

The repo asserts this directly rather than trusting it, in removing_a_node_preserves_the_order_of_the_rest. The test deliberately uses cell-b, because for cell-a the ranking happens to come out in lexical machine order — a test written against that would pass even if the implementation ignored the scores entirely.

E — what falls out for free

The output is a ranking, not a winner

Scoring every machine produces a total order over all of them, and taking the top is one thing you can do with it. Everything else the order gives you costs no extra design.

Second place is the failover target. Not a target you nominated and have to keep in sync — it is what the machine will actually become when the current owner disappears, because that is what the argmax returns over the remaining set. The standby can be told it is the standby without anyone maintaining a standby table.

The top K are the K replicas. Need three copies of every item? Take the first three of the ranking. Every machine computes the same three, in the same order, and when one of them dies the surviving two keep their places while the machine ranked fourth joins the set. A replication scheme with no replication metadata.

term — replica

A machine holding a copy of an item, so the item survives losing one machine. Systems usually keep K of them and need every participant to agree on which K, which normally means storing and distributing that decision. Under rendezvous it is a prefix of a computed list.

A hash ring gives you this too, by walking clockwise, but the walk is a deliberate construction with its own edge cases — a replica set must skip repeated machines, and with virtual nodes the same machine appears at many ring positions. The rendezvous ranking has each machine exactly once, in order, by construction.

F — the costs

Five honest weaknesses

None of these are fatal, and all five are real. Two of them decide whether rendezvous is appropriate for a given system at all, and one of them is visible in this repo's own numbers.

O(N) per lookup Every lookup scores every machine. A hash ring answers in O(log N) with a binary search over sorted ring positions; rendezvous is a linear scan. At ten machines that is ten hashes of a short string — irrelevant, and the absence of a ring to build and maintain is worth more than the difference. At a thousand machines it is a thousand hashes on every lookup and the trade has reversed. Salting the ranking into a two-level tree recovers O(log N), at the cost of the simplicity that motivated the choice.
balance is statistical Each item picks its winner independently, so machine loads follow a binomial distribution, not an even split. With a well-mixing hash the relative spread shrinks as the square root of the item count — a fraction of a percent over a hundred thousand items, but over twenty items across five machines one machine routinely holds twice its share. If items are few, or a few items carry most of the load, the distribution is visibly lumpy and rendezvous does not promise otherwise.
balance is only as good as the hash The statistical argument above assumes the score function mixes: that changing one byte of the key scrambles the whole output. FNV-1a does not, and it shows. Machine ids graph-node-0 through graph-node-5 differ only in the final byte, and FNV-1a folds that byte in with one multiply, so all six scores agree in their top 21 bits and the winner is decided by three low bits of the key hash. Eight equally likely patterns cannot divide evenly among six machines, so two of them win exactly twice as often as the other four — a 2:1 ratio that does not shrink at any item count, because it is not sampling noise. Naming the machines so they differ throughout reduces it to about 1.5:1; it does not remove it. W5 measures both. This is a property of the hash, not of rendezvous, and it is the argument for scoring with a function that actually avalanches.
machines are assumed equal Plain rendezvous gives every machine the same expected share. A fleet with a machine twice the size of the others needs weighted rendezvous, which transforms the score before comparing so that expected share tracks capacity. It preserves minimal disruption and it is a well-understood extension — but it is an extension, with its own formula to get right and freeze. It is not free.
the hash is a wire format This is the one that bites. Two machines running different versions of the scoring function, or feeding it bytes assembled differently, compute different owners — and then disagree about who owns an item. That is precisely the failure the whole scheme exists to prevent, reintroduced by an ordinary refactor. The function, the byte layout of its key, and the tie-break are a frozen wire format, and they have to be treated with the same care as a serialised message on the network.

The last one is why this repo pins four golden hash values in a test rather than merely asserting properties. A property test proves the ranking is deterministic within one build. Pinned hex proves it is the same ranking as last release's build, which is the version running on the pod next to yours during a rolling upgrade. Note what else gets frozen by implication: the scope string is produced by a Display implementation elsewhere in the codebase, so changing that format string reshuffles every item in the fleet.

Neither residue is randomness; both are FNV-1a failing to spread the machine id across the whole 64 bits. Every count is tallied from the real hash, which is why the page can show you this rather than assert balance it does not have.

G — the neighbour

Where this sits next to consistent hashing

Consistent hashing is the other standard answer to the same question, and it solves it well. Both give minimal disruption; the difference is what you build and what you pay.

term — consistent hashing

Hash both machines and items onto one circular number space. An item is owned by the first machine found walking clockwise from the item's position. Removing a machine hands its arc to the next machine clockwise and leaves every other arc untouched — the same minimal-disruption property, reached differently.

With one position per machine the arcs come out very uneven, so real implementations place each machine at many positions — virtual nodes, typically 100 to 500 each. That fixes balance and is the source of most of the mechanism: the ring is a sorted structure you build, hold in memory, and update on every membership change.

rendezvousconsistent hashing
lookup cost O(N) — one hash per machine O(log V) — binary search over V ring positions
state held none; the machine list, which you needed anyway the ring: V sorted positions, rebuilt or patched on change
balance statistical, no tuning parameter statistical, tuned by the virtual-node count
disruption on change minimal minimal
ranking / replicas a full ordering, free clockwise walk, skipping repeats of the same machine
weighting a real extension to the score function give the machine more virtual nodes

Neither is strictly better. Consistent hashing earns its ring at large machine counts and weights naturally. Rendezvous wins when the fleet is small enough that O(N) is noise, when you want a ranking rather than a winner, and when having no structure to build, store, and invalidate is worth more than the asymptotics — which is most often the case at tens of machines rather than thousands.

H — in this repo

What it is used for here

Turbolay uses rendezvous hashing to decide which graph-node is the writer for a cell. The item is a (scope, cell) pair, the machines are the nodes whose heartbeat records are fresh, and the owner is the highest-scoring live node. A node that is not the computed owner declines to promote itself, which is what stopped three nodes from taking turns fencing each other out of one database. The implementation is crates/placement/src/hash.rs; the choice of scheme, the liveness rules it depends on, and the limits of what it guarantees are in write-routing-placement.html.
