The preferred-writer overridea setting nobody set, and the trap it becomes once ownership is enforced

One builder method lets you name the node that should receive writes. Production never calls it, so the value is always whichever node id happens to sort first. That is harmless today for exactly one reason: nothing enforces it. Three widgets below let you drive the moment that stops being true.

A — what the thing actually is

One builder method, one caller, and that caller is a test

Before anything else: the vocabulary. Six words do all the work on this page, and every one of them is defined here rather than assumed.

cell One database file, living in object storage. A deployment has a handful. Reads can come from anywhere; writes to one cell must come from one process at a time, which is the whole subject of this page.
scope Which customer's graph a cell belongs to, written as namespace/graphs/graph_id — for example acme/graphs/social. Two customers can both have a cell called cell-a without colliding.
routing table A short list the server hands a client that says "send reads here, send writes there." It expires after 30 seconds and the client asks again. It is a recommendation, in the way a hotel concierge's restaurant suggestion is a recommendation.
driver The client library inside the application — the thing that holds the routing table and decides which server to dial. Nobody writes this code; it ships with the Neo4j-compatible clients.
fencing The storage layer's way of enforcing one writer. Each writer takes a numbered turn. When a new writer takes turn 18, the holder of turn 17 is fenced: its next write is rejected outright. Like changing the lock — the old key stops working, and nowhere does the door record who has the new key.
rendezvous hashing A way to agree on an owner without anybody being in charge. Every node scores itself for the cell by hashing (scope, cell, its own name), and the highest score wins. Every node computes the same scores, so they all reach the same answer with no messages exchanged — like a room full of people who all sort the same list the same way.

The method

It sets one field on the routing provider, validated against the address map so a bad value fails at construction rather than in production: 

pub fn with_preferred_writer_node(mut self, node_id: impl Into<String>) -> Result<Self> {
    let node_id = node_id.into();
    validate_component("node_id", &node_id)?;
    if !self.node_addresses.contains_key(&node_id) {
        return bolt_config_error("preferred writer node must be present in routing addresses");
    }
    self.preferred_writer_node = node_id;
    Ok(self)
}

The field is read in exactly one place, when the routing table is built. The node named by the field is advertised for WRITE if it answered a health probe; otherwise the first node that did:

That is the punchline. There is no environment variable, no Helm chart value, no config field, and no call site. The method has one caller in the entire repository and it is src/client/bolt/tests.rs:1373. In production the field is therefore always its default, set once in the constructor: 

let preferred_writer_node = addresses
    .keys()
    .next()
    .expect("non-empty address map")
    .clone();

src/client/bolt/routing.rs:76–80 — addresses is a BTreeMap, which keeps its keys sorted, so keys().next() is the alphabetically first node id.

Which node that is, concretely

A three-node deployment sets GRAPH_BOLT_NODE_ADDRESSES to a comma-separated list of id=address pairs. Suppose the config lists them in this order: 

GRAPH_BOLT_NODE_ADDRESSES=
    graph-node-2=graph-node-2.headless:7687,
    graph-node-0=graph-node-0.headless:7687,
    graph-node-1=graph-node-1.headless:7687

The map sorts them, so the advertised writer is graph-node-0 — for every cell, for every customer, always. Nobody chose it. It sorts first. Rename a node or add one whose id sorts earlier, and the advertised writer for the whole deployment moves with no config change and no log line. W1 lets you do exactly that.

B — why it does no damage today

The routing table is a suggestion, and nothing checks it

Today any node that receives a write simply takes over writing. The function that opens the writer, ensure_local_writer (src/engine/cluster.rs:375–390), checks that this process is allowed to be a writer at all and that it holds a shard for the cell. It never asks whether it should be this cell's writer. There is no such question in the code.

So the write lands wherever the client sent it, the node opens the database, takes the next turn number, and the previous holder is fenced. That is the production incident described in write-routing-placement.html: three nodes, one cell, each one taking the turn from the last, forever. 

t=0.00  client A -> graph-node-0   write   node-0 opens Db, claims epoch 17
t=0.31  client B -> graph-node-1   write   node-1 opens Db, claims epoch 18
                                           node-0's next write -> Fenced
t=0.44  client C -> graph-node-2   write   node-2 opens Db, claims epoch 19
                                           node-1's next write -> Fenced
        ... repeats. Every node makes progress on open and none on write.

memory cell-writer-fencing-pingpong

Note what the override is doing during that incident: nothing. Routing advertises graph-node-0 for writes, some clients follow it, others were handed a different node when a probe flapped, and the ones that ignore it entirely are not corrected. A setting that only ever produces a suggestion cannot cause a loop, because there is nothing for it to disagree with.

The override is safe today for the same reason the system is broken today: no node has an opinion about who should own a cell, so no opinion can be contradicted.

C — what changes when the bug is fixed

Two answers to one question, and a loop between them

The fix adds a single branch: a node refuses a write for a cell it does not own. That branch is what makes the override dangerous, and it does so immediately. 

match placement.owner(scope, cell_id) {
    Some(o) if o == self.local_node_id => shard.promote_to_writer(..).await,
    Some(o)                            => Err(GraphError::NotCellWriter { cell_id, owner: o }),
    None                               => shard.promote_to_writer(..).await, // no live owner
}

docs/plans/2026-07-25-rendezvous-placement.md §4, touch point (b) — src/engine/cluster.rs:375–390

After that branch exists, "who is the writer for this cell" has two answers, produced by two different pieces of code reading two different sources:

answercomputed byfromused for
the override routing.rs:235 preferred_writer_node what the routing table advertises to clients
the computed owner cluster.rs:375 owner(scope, cell, live) what the node itself will accept

Set them apart and each component behaves perfectly while the system makes no progress: 

routing says             -> writes for cell-b go to graph-node-0   (the override)
ensure_local_writer says -> graph-node-0 does not own cell-b
                         -> NotCellWriter { owner: graph-node-1 }
driver discards its routing table and asks again
routing says             -> writes for cell-b go to graph-node-0   (the override, again)
                         -> ...

docs/plans/2026-07-25-rendezvous-placement-open-questions.md:1093–1099

Nothing here times out. The refusal is fast and correct, the re-route is the documented driver behaviour for that error code, and the routing table is served exactly as configured. A misconfiguration that validate_component accepts without complaint produces an unbounded loop out of three components that are each doing their job.

W2 The bounce — pick the advertised writer and watch the client loop

Static fallback. Enable JavaScript to choose the override and run the loop.

Try: leave the override on graph-node-0 — the production default — and press "run". Hops climb, refusals climb, commits stay at zero, and they will stay that way as long as you leave it running; press "burst ×200" if you would rather not wait to be convinced. Then switch the override to (deleted) and press run again: one hop per write, no refusals. The owner of cell-b is not asserted anywhere in this widget — it is computed with the frozen hash over the live set, the same call ensure_local_writer makes.

The switch marked driver follows the owner hint models the more generous case. The refusal carries the owner's name, so a driver could dial that node directly instead of re-fetching the table. Turn it on and writes do commit — each one costing a wasted round trip and a refusal, forever, because the routing table it re-fetches afterwards still names the override. Being clever converts a total stall into a permanent tax. It does not exit the loop, because the loop is a disagreement between two sources of truth and no client behaviour can resolve that.

D — the two arguments for keeping it

Both reasons were given in good faith, and both are false

An earlier draft of the placement plan recommended keeping the override. Reading the code reversed that. Here are the two arguments it rested on, and why neither survives.

"We need it for single-node deployments"

The claim is that with one node you must be able to say "that one is the writer". But rendezvous over one live node has exactly one answer, for every cell, by construction: the highest score among one score is that score. There is no second candidate to overrule.

W3 Shrink the fleet — the computed owner collapses on its own

Static fallback. Enable JavaScript for the fleet-size slider.

Try: drag the slider down to one node. Every cell's computed owner collapses to that node and the agreement counter reads four of four — the single-node deployment is the one case where the override is provably redundant. Drag back up and watch the agreement count fall, because the alphabetical default is a fixed answer to a question whose real answer varies per cell. Both columns are computed here: the left by the frozen hash, the right by sorting the node ids, exactly as BTreeMap does.

"We need it for tests"

This one is not merely unnecessary. It makes the test weaker than no test. Rendezvous is a pure, deterministic function of three strings, so a test can compute the expected owner the same way the production code will. Pinning the answer instead means the assertion no longer depends on the computation at all.

Today, at src/client/bolt/tests.rs:1371–1389:

let preferred = provider
    .clone()
    .with_preferred_writer_node("node-b")          // force the answer
    .unwrap()
    .routing_table("default", &target)
    .await
    .unwrap();
assert_eq!(write_addresses(&preferred), vec![fallback_address.clone()]);
// passes even if placement is completely broken: nothing here consults it

What it becomes:

let live = ["node-a", "node-b"];
let expected = turbolay_placement::owner(&target.scope.to_string(), &target.cell_id, &live)
    .expect("a live node exists");
let table = provider.routing_table("default", &target).await.unwrap();
assert_eq!(write_addresses(&table), vec![address_of(expected)]);
// now the test fails if routing and placement ever disagree, which is the bug

The second version asserts the property that matters — routing advertises whoever placement names — instead of asserting a hardcoded string. It also gets stronger for free every time the placement crate changes, because it re-derives its expectation. This is the same discipline the sibling page's heartbeat widget uses: it picks cell-b precisely because cell-b's owner over three nodes really is graph-node-1, computed rather than asserted.

There is a trap in the other direction worth naming, since the plan documents it: over graph-node-0..3, cell-a happens to rank in plain alphabetical order. A test written against cell-a would pass even if ranking ignored the score entirely. Computing the expectation is necessary; computing it against an input that can distinguish right from wrong is the other half.

E — the decision

Delete it, or move it inside the thing it would otherwise contradict

what it meanswhat it costs
B1 — delete it recommended Remove with_preferred_writer_node and the preferred_writer_node field. Rendezvous becomes the only writer selection, so routing and ensure_local_writer cannot disagree because there is only one of them. Rewrite bolt/tests.rs:1373 to compute its expectation. One method, one field, one test. No configuration surface is lost, because none was ever exposed.
B2 — move it into placement as a pin If an operational pin is genuinely wanted, it belongs inside owner() in turbolay-placement, consulted before the hash. Routing and the node then both derive from one source and cannot disagree, which is the property that makes B2 safe where the status quo is not. Config plumbing to get the pin to every node; validation that the pinned node is live; and a decision, with a test, about what happens when it is not — fall back to the hash, or refuse writes and honour the operator.

B2 is a real design, not a straw man, and its cost is mostly in that third item. "The pinned node is dead" has no obviously correct answer: falling back to the hash silently discards the operator's instruction at the moment they most likely meant it, and refusing writes turns a typo into an outage that self-heals only when someone notices.

The recommendation is still B1, on the narrowest possible grounds: nobody has ever pinned a writer in production, because nobody could. There is no env var and no chart value. B2 spends real work, and a permanent branch in the ownership function, on a requirement that has never been stated by anyone. If a pin is wanted later it is a small addition to a crate that will already exist, and designing it then means designing it against a real operational need rather than a guessed one.

Either way the fallback beneath the override goes too. reachable.first() (routing.rs:238) moves whenever a 250 ms health probe flaps, so two clients asking at slightly different instants can be handed different writers. That instability is half of what Q2 deletes when the probe fan-out is replaced by heartbeats.

summary

Dead configuration is not neutral; it is waiting

The override has been safe for a reason that reads, in hindsight, as an accusation: it was safe because nothing in the system enforced ownership, so no setting could contradict one. It was harmless in the way an unwired light switch is harmless. Fixing the writer duel is what wires it up.

The general shape is worth keeping past this decision. When a system gains a computed invariant, every existing setting that names the same thing by hand becomes a second source of truth for it, and the two will eventually be set apart by someone with good intentions. There are only two safe endings: the setting is deleted, or it is moved inside the computation so that there is still only one answer. What is not available is leaving it where it is, next to the invariant, disagreeing with it in a way that validates cleanly and loops forever.
