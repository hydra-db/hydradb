A — the reference implementation

How TiDB gets a write to the right node

Read this as a shape, not a shopping list. The mechanisms matter; the components they run on mostly don't transfer.

TiKV splits the keyspace into regions — contiguous key ranges, the structural equivalent of a Turbolay cell. Each region is a Raft group, and its leader is the only peer that may accept a write. So far this is Turbolay's problem exactly: a partition with one legal writer.

The first difference is decisive and worth naming before anything else. Raft elects; SlateDB fences. A TiKV region always has an elected leader that the peers themselves agreed on, and a follower that receives a write knows it is not the leader and who is. A SlateDB database has whichever writer most recently opened it, and a fenced writer only learns it lost after the fact. TiKV's routing layer therefore starts from an authoritative answer it can publish; Turbolay's has to manufacture one.

Four mechanisms, in the order a write meets them

1 — PD holds the authoritative map. The Placement Driver stores region → peers → leader, fed by region heartbeats. It also schedules: splitting hot regions, merging cold ones, transferring leaders to balance load. TiDB additionally expresses placement intent to PD through affinity groups — CreateAffinityGroupsIfNotExists asks PD to co-locate a set of key ranges, and does so idempotently precisely so it stays correct across a DDL owner switch or a network failure mid-retry.

tidb-master · pkg/domain/affinity/interface.go:47–56, manager.go:56–72

2 — The client caches the map, and the hot path never asks PD. client-go's RegionCache resolves a key to a KeyLocation locally. TiDB's coprocessor layer builds request batches straight out of those cached locations. A PD round trip on every write would defeat the entire design.

tidb-master · pkg/store/copr/region_cache.go — tikv.KeyLocation throughout

3 — Errors correct the cache; the write is never bounced back to the user. This is the mechanism Turbolay is missing entirely. TiKV replies with a typed region error — NotLeader (carrying a leader hint), EpochNotMatch, RegionNotFound, StaleCommand — and the client invalidates its cache with the reason attached, backs off, and retries:

tidb-master · pkg/store/copr/batch_coprocessor.go:1556 · pkg/store/copr/mpp.go:187 b.store.GetRegionCache().InvalidateCachedRegionWithReason(id, tikv.EpochNotMatch)

A stale routing table is treated as an expected, routine condition with a defined recovery, not as an error. The application never sees it.

4 — For singleton work, TiDB skips routing altogether. DDL has exactly one legal executor cluster-wide, which is the same single-writer shape at a coarser grain. TiDB does not route DDL statements to the owner. Any node accepts the statement; JobSubmitter writes it into a system table and notifies; only the owner's scheduler picks it up.

jobScheduler is used to schedule the DDL jobs, it's only run on the DDL owner.

tidb-master · pkg/ddl/job_scheduler.go:132

The owner itself comes from an etcd election — ownerManager wrapping concurrency.Election with a lease TTL. It is worth reading that file for its scar tissue rather than its API: the comments around ForceToBeOwner document a real production incident (issue #54689) where multiple owners coexisted during a mixed-version rolling upgrade, mitigated by deleting all campaign keys and putting the new one in a single transaction, plus a deliberate sleep to let the cluster settle.

tidb-master · pkg/owner/manager.go:179–262

That is the cost of a real election service, paid by a team that already had etcd for other reasons. It is exactly the cost Turbolay's architecture and sleet's RFC both decline to pay.

B — what transfers

Two mechanisms port cleanly; the third needs a substitute

TiDB / TiKV mechanism what it buys Turbolay status
Region → leader map in PD one authoritative answer to “who may write this” substitute needed no map exists; PD is ruled out by R7
Client-side region cache with TTL no lookup on the hot path already present the Bolt routing table is this — it just answers the same thing for every cell
NotLeader / EpochNotMatch, invalidate-with-reason, backoff wrong-node writes self-correct within a bounded number of retries missing entirely a fenced write returns an opaque error; the driver retries into the same node
DDL: submit to a table, owner executes routing becomes optional for a class of writes partially available node-to-node transport exists; ack semantics would have to change
PD region split / merge / leader transfer partitions resize and rebalance under load out of scope cells are static config — GRAPH_CELLS, identical on every node

The middle row is the highest value-per-line change available, and it depends on nothing except a way to name the owner.

The one thing that emphatically does not transfer is PD itself, and the reason is structural rather than a matter of taste. TiDB can afford a placement driver because Raft already requires a cluster manager — PD is incremental cost on a dependency that must exist. Turbolay's premise is the opposite:

The design uses object storage, the shared service every SlateDB deployment already has. Adding ZooKeeper, etcd, or a custom coordinator would make safety depend on another system.

sleet — rfcs/0001-design.md, “Motivation”

So the question narrows usefully: take TiKV's protocol shape — cached map plus error-driven correction — and get the map from somewhere that costs nothing to operate.

C — sources of truth

Four places the ownership map could live

OPT-1

Compute it — rendezvous hashing over live nodes

adopt

reference: sleet — src/placement.rs, rfcs/0001-design.md “Placement”

Store no assignment at all. Every node derives the same answer from the same inputs: the cell identity and the set of live nodes.

the whole mechanism owner(scope, cell) = argmaxn ∈ live H(scope ‖ 0x00 ‖ cell_id ‖ 0x00 ‖ node_id)

Liveness comes from heartbeat objects, not from probes: a node is live if its heartbeat object is younger than heartbeat_timeout, timestamped by object storage rather than by any local clock. sleet treats the hash and its key encoding as a frozen wire format with a golden test, because mixed-version fleets must compute identical owners. Removing a node moves only the cells it owned; adding one moves only the cells it now wins — sleet has a test for exactly that property.

Turbolay already has the membership half. ObjectStoreNodeDirectory holds validated cell ids and node ids and is threaded through every cluster constructor. What it lacks is a liveness dimension, which is a heartbeat prefix and a LIST.

src/engine/cluster.rs:101–160

buysR2 and R7 together — an ownership answer with zero new dependencies and zero stored state
costsduring view skew two nodes can both believe they own a cell; convergence bounded by heartbeat_timeout plus one tick
riskthe hash becomes a compatibility surface the moment two versions run together
OPT-2

Store it — a CAS-held lease object per cell

hint only

reference: the pattern PD implements, reduced to object storage

Put .../<cell-id>/_writer in the store holding {node_id, epoch, expires_at}, acquired and renewed with conditional PUT. Ownership becomes explicit, inspectable by an operator, and a natural place to hang the WRITE routing address.

The problem is that it creates a second source of truth for a question SlateDB's writer epoch already answers, and the two can disagree. A node holding a valid lease can be fenced; a fenced node can hold a valid lease. Whichever one you trust in that moment, you have contradicted the other. sleet declines this explicitly — “Sleet does not add a lock service” — and Turbolay's architecture rules out a writable controller in the data path.

buysexplicit, operator-visible ownership; a stable place to publish the write address
costslease renewal on the write path, clock-skew semantics, two authorities for one question
verdictviable only as an advisory object that records what OPT-1 computed — never as the authority
OPT-3

Elect it — an external election service

rejected

reference: tidb-master — pkg/owner/manager.go

The strongest ownership semantics available: a real lease, real fencing on the control plane, and mature primitives for the hard cases — ResignOwner, ForceToBeOwner, BreakCampaignLoop for rolling upgrades.

It fails R7 by construction, and TiDB's own comments are the argument against adopting it casually: the mitigations around issue #54689 exist because even with etcd, even with a mature implementation, multiple owners appeared during a mixed-version upgrade. An election service does not remove the need to be safe under split ownership — it just changes how often you are.

buysthe strongest possible answer to R2
costsa hard dependency in the data path; violates R7 and architecture.md:26–27
verdictcite as the thing deliberately not being done, and why TiDB can afford it
OPT-4

Sidestep it — forward the write to the owner

complement

reference: tidb-master — pkg/ddl/job_submitter.go, job_scheduler.go

TiDB's DDL answer: don't route, accept anywhere and deliver internally. Turbolay is unusually well positioned for this because the transport already exists — QueryServiceEndpoint and QueryServiceDirectory give node-to-node RPC with TLS and mTLS, bearer auth, per-principal scope authorization, frame limits, connection pooling, and cancellation.

src/query/coordination.rs:1282–1331

This turns routing into a pure optimization: a wrong-node write costs one extra hop instead of an epoch bump and two cold caches. But note what it does not solve — the forwarding node still has to know who the owner is, so OPT-4 sits on top of OPT-1 rather than replacing it.

The queue variant (append to a per-cell intake, owner drains) goes further and collides with a stated contract: acking on enqueue is not acking on durable commit.

E — proposal

Three layers, in dependency order

Numbered because each layer is genuinely useless without the one above it. Layer 1 is a prerequisite, not a preference.

1

Make the cell addressable, and derivable

Nothing else is possible while cell_id is a process constant. Either extend the database-name grammar so a cell is nameable alongside the tenant scope, or derive it from the statement itself.

The derivation machinery already exists and is not wired to the client path: locality_cell_id and LocalityCellExtractor already extract a cell from a key, and compare_locality_layouts already reports how cleanly a key set partitions. Turbolay knows how to answer “which cell does this key belong to”; the resolver has just never been asked.

src/placement.rs:30–102 — extractor, prefix, and layout experiment, all unused by the client path

Satisfies R1. Everything below is blocked on this.

2

Compute ownership, and publish it through the routing table

Add heartbeat objects under the scope root and give ObjectStoreNodeDirectory a liveness dimension. Freeze a rendezvous hash with the same discipline sleet applies — frozen key encoding, tie-break by node id, a golden test that fails loudly when either changes.

Then let routing_table finally read the arguments it already receives: WRITE becomes the address of owner(target.scope, target.cell_id); READ and ROUTE stay as all live nodes. This is a contained change to a function that has been handed the right inputs since it was written.

Drop the per-ROUTE /readyz fan-out in favour of heartbeat freshness. That removes N TCP connects per routing refresh and — more importantly — makes liveness consistent between two clients asking at the same moment, instead of per-caller.

Satisfies R2, R3. The result is TiKV's region-cache shape without PD: a driver caching a correct, per-cell write address for a TTL.

3

Make wrong-node writes self-correcting, and bound the duel

This is the layer with no current analogue anywhere in the codebase, and the highest value per line. Three changes, in order of importance:

the rule that ends the duel A node MUST NOT promote itself for a cell it does not own,
unless the computed owner is not live.

That single rule converts “any node steals the epoch on demand” into “only a node with a placement reason claims the epoch.” It is the difference between F-05 being unbounded and being bounded.

Second: map the not-the-owner condition to Neo.ClientError.Cluster.NotALeader on Bolt, carrying the computed owner as a hint — exactly TiKV's NotLeader{leader_hint}. Drivers already know what to do with it: discard the routing table, re-route, retry. For HTTP and batch clients that cannot re-route, forward over the existing QueryServiceEndpoint transport instead.

Third: adopt sleet's fenced-task discipline. A writer that discovers it was fenced waits one heartbeat interval before re-promoting, giving the rival the same opportunity to stand down. The oscillation is then bounded by the same quantity as view convergence, rather than by nothing.

Satisfies R4, R5.

F — invariants preserved

What none of this changes

safety The SlateDB writer epoch and WAL barrier remain the only mutual-exclusion mechanism. Placement never gains authority. If the router is wrong, writes stay correct and only get slower — the property sleet states as “safety never depends on sleet's scheduling.”
reads Unchanged. Every ready query node continues to serve reads for every configured cell, from its own pinned snapshot. Both consistency modes and the indexed-base-plus-WAL-tail overlay are untouched.
dependencies Object storage stays the only coordination dependency. No consensus service, no writable graph controller, nothing new in the data path.
durability A successful API return still means the mutation reached SlateDB's durable commit point — provided the queue variant of OPT-4 stays out of scope.
indexers Unaffected. They never become writers, and content-addressed generations plus CAS on the current pointer already tolerate duplicate work.

G — unresolved

Open questions worth settling before implementation

Where does cell derivation live — resolver or planner?

Deriving the cell from the tenant scope is a resolver concern. Deriving it from the keys a statement touches is a planner concern, and a statement can touch keys in more than one cell. The answer determines whether layer 1 is a small change or a planning change.

Multi-cell writes and bookmarks

Once cells are independently routable this becomes urgent rather than theoretical. Two cells means two transactions, two owners, two bookmarks and no atomicity. Decide whether to reject such statements, split them with per-cell bookmarks, or define a composite bookmark — before layer 1 makes them reachable.

Rebalancing has no dampening

Rendezvous moves ownership the instant the live set changes. A node that flaps takes its cells back each time it returns, and each move is a writer open. PD has explicit leader-transfer scheduling and evict-leader for this; rendezvous has nothing. A hysteresis term or a minimum-tenure rule probably belongs in layer 2.

Cells are static; regions are not

PD splits hot regions and merges cold ones continuously. Turbolay cells come from GRAPH_CELLS, identical on every node, fixed at process start. Nothing here addresses a hot cell — routing it correctly to one writer is exactly what makes it a bottleneck. Cell splitting is a separate problem and a larger one.

The hash becomes a compatibility surface

sleet freezes its hash, key encoding and tie-break, and pins them with a golden test, because mixed-version fleets must agree on owners. Turbolay would inherit the same obligation from the first release that ships layer 2. Worth deciding the key encoding deliberately rather than discovering it is load-bearing later.

summary

The short version

Turbolay has the client-side cache TiKV has, and is missing both the map and the correction. sleet already demonstrates that the map can be computed rather than stored, on the same primitives and in the same organisation. The correction is a Bolt error code and one rule — do not promote for a cell you do not own — and it is the change that turns an unbounded promotion duel into a bounded one.
