Placing the writerrendezvous, heartbeats, and the bounded duel

vocabulary — before section A

The terms the rest of this page assumes

Everything below is used without further introduction. The first five carry the rest.

termmeaning
Cell One SlateDB database. Admits exactly one writer at a time. The unit ownership is computed for.
Writer / writer epoch The node currently allowed to write a cell. SlateDB stamps a number into the manifest on open; a higher number wins.
Fenced You were the writer, another node opened the cell with a higher epoch, and your next write fails. The production incident is three nodes doing this to each other in a loop.
Graph-node One of the server pods (graph-node-0/1/2). Serves Bolt, can read any cell, may write only the cells it owns.
Client / driver The Neo4j Bolt driver inside the customer's application. Sends queries, caches routing tables, retries. Not a person, and not our code.
Routing table What the driver receives in reply to a ROUTE request: which nodes to read from, which single node to write to, and a TTL.
Scope {namespace}/graphs/{graph_id}, the database name the driver sends — for example acme/graphs/social.
Tenant The customer; the namespace part of the scope.
Owner The node rendezvous says should write a given cell. Computed on demand, never stored.
Rendezvous hashing Score every (cell, node) pair; the highest score wins. Every node reaches the same answer with no coordination.
Heartbeat A small object each node writes every 5s, meaning "alive and ready". Liveness comes from the object's timestamp, never a local clock.
Live set The nodes with a fresh heartbeat; the candidate list rendezvous chooses from.
Promotion A node opening a cell for writing and claiming the epoch. The action that must be restricted to the owner.

A — the incident

Three nodes, one cell, an epoch counter going up forever

This is not a hypothetical. It is a production trace, and it is the reason the turbolay-placement crate exists.

All three graph-nodes were configured with the same GRAPH_CELL_ID, so every client write targeted the same cell. Nothing in the system decides which node should be that cell's writer, so any node that received a write opened the Db, claimed a new epoch, and fenced whoever held it. 

t=0.00  client A -> graph-node-0   write   node-0 opens Db, claims epoch 17
t=0.31  client B -> graph-node-1   write   node-1 opens Db, claims epoch 18
                                           node-0's next write -> Fenced
t=0.44  client C -> graph-node-2   write   node-2 opens Db, claims epoch 19
                                           node-1's next write -> Fenced
t=0.52  client A retries -> node-0          node-0 reopens, claims epoch 20
                                           node-2's next write -> Fenced
        ... repeats. Every node makes progress on open and none on write.

memory cell-writer-fencing-pingpong, reproduced in docs/plans/2026-07-25-rendezvous-placement-open-questions.md:312–321

Two distinct failures are stacked here, and separating them is the whole shape of the fix. The first is the duel itself: no node has a reason to stand down, so the oscillation has no reason to stop. The second is diagnostic. All three logs say only Fenced. None says by whom. You are debugging three identical lines, each of which reports "someone took it from me."

B — why nothing decides

Two independent gaps, both of them silent

Doc 1 traced the write path from the Bolt socket to the WAL commit and found no step that asks who should own the cell. Two pieces of code make that concrete, and both are worth reading before the fix, because the fix is shaped by them.

The routing table picks a writer, and the pick is unstable

There is a writer-selection mechanism today. It is part of the bug: 

let writer = reachable
    .iter()
    .find(|(node_id, _)| node_id == &self.preferred_writer_node)
    .or_else(|| reachable.first())
    .expect("reachable node list was checked")
    .1
    .clone();

src/client/bolt/routing.rs:235–241

reachable is whatever answered a 250 ms /readyz probe on this particular call, so the reachable.first() fallback moves whenever a probe flaps. Two clients probing at slightly different instants can be handed different writers. The selection is per-caller, and it is not sticky.

And whatever routing decides, the node ignores it

ensure_local_writer (src/engine/cluster.rs:375–390) checks that this process is promotable and that it holds a shard for the cell. It never asks whether it should be the writer. Routing's opinion is advisory and unenforced. That gap — an unstable suggestion plus an unconditional promotion — is the ping-pong.

So the fix needs exactly two things that do not exist: a stable, cluster-wide answer to "who owns this cell", and one node-side branch that respects it.

C — rendezvous placement

The answer is computed, so nobody has to store it

Landed as the crate turbolay-placement in crates/placement, ported from ../sleet/src/placement.rs.

the whole mechanism owner(scope, cell) = argmaxn ∈ live H(scope ‖ 0x00 ‖ cell_id ‖ 0x00 ‖ node_id)

No stored assignment, no lease, no election service. Every node computes the same answer from the same object-store LIST. The function is thirty lines and has no dependencies: 

pub fn score(scope: &str, cell_id: &str, node_id: &str) -> u64;
pub fn rank<'a>(scope: &str, cell_id: &str, live: &[&'a str]) -> Vec<&'a str>;
pub fn owner<'a>(scope: &str, cell_id: &str, live: &[&'a str]) -> Option<&'a str>;

crates/placement/src/hash.rs:35, :47, :63

The hash is a wire format, and it is frozen

FNV-1a 64 — offset 0xcbf29ce484222325, prime 0x100000001b3, wrapping multiply — over scope ++ 0x00 ++ cell_id ++ 0x00 ++ node_id, ranked descending by score with ties broken by node id ascending. Changing any part of that splits a mixed-version fleet into two disagreeing views of who owns a cell, which is the exact failure the crate exists to prevent. The separator is load-bearing: without it ("ab", "c") and ("a", "bc") hash alike.

scope is GraphScope's Display — "{namespace}/graphs/{graph_id}" (src/core/namespace.rs:268–272). Pinning golden values against it freezes that impl as a wire format too. Changing the format string reshuffles every cell in the fleet.

Minimal disruption is the property that makes it usable

Removing a node preserves the relative order of the survivors. One failure therefore moves only that node's cells, rather than reshuffling the fleet. That is asserted directly — removing_a_node_preserves_the_order_of_the_rest (hash.rs:124–132), and deliberately against cell-b: under cell-a the ranking happens to come out in lexical node order, so a test written against it would pass even if rank ignored the score entirely.

D — the don't-promote rule

One branch converts theft into a placement decision

Rendezvous on its own changes nothing in production. It is a pure function; it has no effect until a node consults it and is willing to say no. That is touch point (b), in RoutedGraphCluster::ensure_local_writer (src/engine/cluster.rs:375–390): 

match placement.owner(scope, cell_id) {
    Some(o) if o == self.local_node_id => shard.promote_to_writer(..).await,
    Some(o)                            => Err(GraphError::NotCellWriter { cell_id, owner: o }),
    None                               => shard.promote_to_writer(..).await, // no live owner
}

The third arm matters as much as the second. None means placement has no opinion, not nobody may write (hash.rs:57–62). If no node is live — which, given a node always counts itself live, means the LIST returned nothing usable — refusing every write would trade a bounded stall for a total outage. This one branch is what converts "any node steals the epoch on demand" into "only a node with a placement reason claims it."

The refusal has to reach the driver, or it accomplishes nothing

GraphError::NotCellWriter { cell_id, owner } maps to the Bolt error code Neo.ClientError.Cluster.NotALeader, carrying the owner as a hint — modelled directly on TiKV's NotLeader{leader_hint}. Drivers already know this code: discard the routing table, re-route, retry.

Today the Bolt module has exactly one Neo code (src/client/bolt.rs:1366, Neo.TransientError.Transaction.Terminated), so a fenced write is opaque and the driver retries into the same wrong node. Without the error code, the refusal is a correct answer that the client cannot act on: 

without the code:  client -> graph-node-2 (not the owner)
                   node-2 returns a generic error
                   driver has no reason to discard its routing table
                   driver retries -> graph-node-2 -> same error -> ...

with the code:     node-2 returns Neo.ClientError.Cluster.NotALeader, owner=graph-node-1
                   driver discards the routing table, re-routes, retries
                   -> graph-node-1 -> ok

docs/plans/2026-07-25-rendezvous-placement-open-questions.md:768–777

HTTP clients cannot re-route, so ClientHttpServer returns 421 with the owner in the body. Forwarding over the existing QueryServiceEndpoint transport is the better answer for HTTP, and is a follow-up rather than part of this change.

W1 above implements exactly this pair. With rendezvous ON, watch the log: the non-owner emits NotCellWriter, the simulated driver re-routes, and the retry lands on the owner without an epoch bump.

E — liveness

Heartbeats replace the per-request /readyz fan-out

Rendezvous needs a live set. Turbolay computes one today, badly, on every single ROUTE request.

What happens today

Every ROUTE request makes the receiving node open a TCP connection to every node's admin port and hand-write GET /readyz HTTP/1.1, all of them concurrently through join_all: 

async fn reachable_nodes(&self) -> Vec<(String, String)> {
    let probes = self.node_addresses.iter().map(|(node_id, address)| { ... });
    join_all(probes).await.into_iter().flatten().collect()
}

async fn probe_node_readiness(address: &str, probe_timeout: Duration) -> bool {
    let mut stream = TcpStream::connect(address).await?;
    let request = format!("GET /readyz HTTP/1.1\r\nHost: {address}\r\nConnection: close\r\n\r\n");
    ...
}

src/client/bolt/routing.rs:152–168, 196–218 — the fan-out

One driver question becomes N TCP connections. Worse than the cost: each node probes independently, so two nodes can disagree about who is up at the same instant. Feeding an inconsistent liveness view into a placement function whose entire value is that everyone computes the same answer defeats the point.

The fan-out counter is the product of the two and grows quadratically as a fleet scales in both dimensions; the LIST counter grows only with driver count. The heartbeat PUT rate is shown alongside because it is the cost you are buying instead — and it is linear in nodes, not in drivers.

What replaces it

Each node PUTs a small object every heartbeat_interval: 

publish loop:  every heartbeat_interval, if AdminState.ready { PUT <base>/_graph_nodes/v1/<node-id> }
                                         else                { DELETE it if present }
SIGTERM:       DELETE <base>/_graph_nodes/v1/<node-id>, then drain
liveness:      node is live iff its object exists and now - LastModified < heartbeat_timeout

Liveness comes from the object's LastModified as reported by object storage, never a local clock. That is sleet's rule (../sleet/src/root.rs:147, 209) and it is why nodes with skewed clocks still agree on the same live set. Placement reads only the LIST result — name and timestamp. Bodies are observability and are never fetched on the placement path. Following sleet, a node always counts itself live (../sleet/src/daemon.rs:124–131): if its own heartbeat looks stale it has no reliable proof it should stop.

The catch: Bolt clients never touch a k8s Service

This is the fact that makes deleting the fan-out non-obvious, and skipping it is how you ship an outage. Bolt clients connect directly to pod addresses handed out by GRAPH_BOLT_NODE_ADDRESSES (charts/turbolay/templates/configmap.yaml:44). The k8s readinessProbe gates Service endpoints, and no Bolt client is using the Service — so k8s readiness does not gate Bolt traffic at all.

That is precisely why routing.rs probes independently. Deleting the fan-out without replacing the signal would advertise unready nodes to drivers. The replacement is the readiness gate on publication above: a node publishes a heartbeat only while AdminState.ready, and DELETEs it on graceful shutdown. Readiness then propagates through the same channel as liveness, and both are consistent across callers.

Note what this catches that a plain TCP-reachability check would not: a node whose Bolt listener is bound and accepting while it is still opening the object store and warming state. The /readyz probe catches that today; readiness-gated heartbeats catch it too; deleting the probe without the gate would not.

The regression, stated precisely

On a graceful shutdown the heartbeat is DELETEd in the SIGTERM handler, so the very next LIST omits the node. Detection is immediate — the same as today, and this is the majority of real restarts.

On a hard crash — OOM kill, SIGKILL, no shutdown hook — the heartbeat object lingers until it ages out. Reads are fine: the driver dials the dead pod, gets ECONNREFUSED, and routes around it itself, with no help from placement. Writes to cells the dead node owned fail for up to heartbeat_timeout, because placement still names the dead node as owner and every live node correctly declines.

Then it self-heals with no operator action: the heartbeat ages out of the live set, placement recomputes over the survivors, and the new owner promotes on the next write. Today that stall is roughly 250 ms via the probe. But today the alternative to a stall is an unbounded duel, so the trade being made is unbounded → 15s, not good → bad.

Choosing the two numbers

Tighter is not free, and the cost is not the PUTs. Rendezvous moves ownership the instant the live set changes, and this design has no rebalance dampening — deliberately out of scope. So a node that flaps in and out reclaims its cells every time it returns, and every reclaim costs a writer open: a manifest CAS and an epoch bump.

W5 Timeout trade-off — detection latency against flap churn

Static fallback. Enable JavaScript for the sliders.

Try: leave the flap at 10s and walk the timeout down from 30s to 6s. It reads zero until the timeout drops below the flap, then jumps — that is the moment the node starts ageing out of the live set on every blip and ownership begins bouncing, each bounce a manifest CAS and an epoch bump. Push the timeout back up and dead-node detection gets worse instead. The worst case for any timeout sits just past it, which is why the curves peak rather than rise. 5s/15s is marked: it absorbs a 10s flap and still detects a real death in 15s. Setting interval >= timeout is rejected here the same way startup validation rejects it.

The pricing in that widget is the same arithmetic as the decision record: one small object PUT per node per interval, at roughly $0.005 per 1,000 S3 Standard PUTs. Three nodes at a 5s interval is about 52,000 PUTs a day and about $8 a month — noise. A hundred nodes at 2s is about $650 a month, which is why the interval is config and not a constant.

If flapping turns out to hurt in practice, the fix is a minimum-tenure rule — an owner keeps a cell for at least T after acquiring it — not a longer timeout. That is a recorded follow-up, not part of this change.

F — the honest headline

The duel is bounded, not prevented

This is the claim the whole design rests on, and it should be said plainly rather than buried. Two nodes can still both believe they own a cell, briefly. Nothing here makes that impossible.

The evidence that this is workable is not a proof we wrote. It is ../sleet, which runs this architecture at fleet scale on the same storage primitives, in the same organisation.

What sleet actually does

Sleet never opens a SlateDB Db at all. There is not one Db::builder, Db::open or DbBuilder in sleet's src/; every hit is in tests/. The only handle it constructs is slatedb::admin::Admin (../sleet/src/services.rs:71–91). So sleet is never a writer and never takes a writer_epoch — its analogue is compactor_epoch ping-pong between two compaction coordinators. Same shape, different epoch. Read every sleet claim below with that substitution in mind.

No lease object exists. Sleet stores exactly three things under the fleet root: sleet.toml and dbs/<db>.toml for operator intent, and nodes/<id>.<letters>.json for liveness plus offered roles. The heartbeat is an unconditional PUT — no PutMode, no ETag, no UpdateVersion (../sleet/src/daemon.rs:292). It says "I am alive and I offer these services." It never says "I own database X." Sleet stores liveness and intent, and recomputes ownership from the frozen hash every tick.

A non-owner simply has no key in the owned map, so it never spawns the task; a running task whose key is absent is cancelled on the next reconcile (../sleet/src/daemon.rs:117–162, :327–353). Absence, not refusal.

The fence handler, which is the part to copy exactly

let delay = match result {
    Ok(()) => break,
    Err(e) if e.is_fenced() => {
        info!(database = %url, "coordinator fenced; retrying after one heartbeat interval");
        backoff = Duration::from_secs(1);
        heartbeat_interval
    }
    Err(e) => {
        warn!(database = %url, service = service.as_str(), "task failed: {e}");
        backoff = (backoff * 2).min(MAX_BACKOFF);
        backoff
    }
};

../sleet/src/daemon.rs:458–472

Three details, all of them deliberate. A fence resets the exponential backoff to 1s rather than advancing the ladder — a fence is treated as view skew, not as a failure, and without the reset a merely-converging node backs off to minutes and looks dead. The wait is exactly one heartbeat_interval, sized to let the rival refresh its view and stand down; it is not a politeness delay. And the retry is unconditional: it does not re-check ownership. Rerun, and let the outer loop cancel you if you were wrong. Sleet accepts that a fenced node will re-fence the winner once more before converging.

Double-running is permitted by design, and asserted by the model

Sleet does not add a lock service. SlateDB's manifest CAS, epochs, and compaction job claims remain the mutual exclusion mechanisms.

Sleet treats placement as an efficiency decision. Safety belongs to SlateDB.

../sleet/rfcs/0001-design.md:35–37, :251–260

The model checker does not try to rule the double-run out. It asserts that it is reachable: 

# The design's stated worst case, a transient double-run, is
# reachable in the model.
exists assertion DoubleRunReachable:
    return len([db for db in DBS if len(runners[db]) > 1]) > 0

../sleet/specs/coordination.fizz:167–175

Paired with it is a Converged liveness property — an eventually always requiring the expected single runner and no outstanding fences after churn stops — whose stated purpose is to catch fence livelock, because a livelock would flap runners and fences forever and violate eventually-always. Sleet does not claim the duel cannot happen. It claims the duel is bounded, and it proves the bound: config_poll plus one heartbeat tick, with "the cost is a short compaction stall."

Sleet even counts itself live when its own heartbeat looks stale (../sleet/src/daemon.rs:124–130), deliberately choosing overlap over gaps: peers that consider it dead take over in parallel, which is a safe double-run, whereas excluding itself would leave the share unowned.

Where we deviate, in both directions

sleetthis design
Placement rendezvous, recomputed each tick same, crates/placement
Ownership stored? no advisory record only — see section G
Ownership checked where once, at task spawn, in the supervisor every promotion — stricter than sleet
On a fence reset backoff to 1s, wait one interval, retry unconditionally match exactly, touch point (d), src/core/state.rs:235–246
Mutual exclusion delegated to SlateDB epochs; duel bounded, not prevented same
On a failed LIST of the node directory keep current assignments (daemon.rs:243) must differ — proposal is to shed ownership
Verified by Fizz model, Converged liveness property an integration test: 3 nodes, 1 cell, concurrent writes, exactly one epoch bump

Stricter than sleet, in one place. Sleet checks ownership once at task spawn and never again, so a task keeps running through an ownership change until the next reconcile tick. Touch point (b) checks on every promotion. That is a better guarantee and costs nothing, because the live set is already in memory.

And one place we must not copy sleet. On a failed LIST of the node directory sleet keeps its current assignments. For a compaction coordinator that is a safe double-run. For a writer it is an unbounded duel by construction: a node partitioned from the object store can never learn that it lost ownership, so it re-promotes forever against a node that thinks it won. Shedding on the first failed LIST is the opposite extreme and drops a healthy writer on one throttled request. The rule is bounded: keep the last good view while it is younger than heartbeat_timeout, then go unready, DELETE the heartbeat, and refuse promotion with no owner hint.

The grace is heartbeat_timeout rather than a new knob because peers take over that long after the last successful PUT, and in a partition LIST and PUT fail together. A shorter grace leaves a window where nobody owns the cell; a longer one leaves a duel; equal makes the two coincide. The part that is easy to miss is that shedding has to withdraw the heartbeat. In a partial failure — LIST throttled, PUTs still landing — a node that sheds while still publishing stays the computed owner for everyone else, so peers route writes to it and it refuses every one, permanently, with nothing left to time out. Withdrawing makes peers take over, and it falls out of the readiness gating for free: a node that cannot read the live set is not ready. Worst case for the cell is the 15s grace plus peer detection — immediate if the DELETE lands, another 15s if the store is fully unreachable. Thirty seconds, against sleet's forever.

G — the lease

An authoritative lease is not implementable, so the record is advisory

The obvious instinct is a CAS-held lease object naming the writer. The obstacle is not philosophical — not "two authorities" — it is that the primitive does not exist. Three things confirmed against the tree:

readable VersionedManifest::writer_epoch() is public via DbStatus.current_manifest. It is already a CAS-backed, monotonic, observable lease.
no identity The manifest records "epoch 18". It never records "graph-node-1 holds epoch 18". You can detect that you were fenced; never by whom. That missing identity is the entire gap a lease object would fill.
no hook There is no fence-before-open hook. Db::builder has no expected_epoch and no skip_fence; build() unconditionally claims a new epoch. Verified absent from both the usecortex fork and upstream slatedb 0.14.1.

The third point is decisive. A lease object cannot prevent anything, because SlateDB never consults it. It can only stop a node that already chose to check. That is advisory, whatever we call it.

What is being built instead

After a successful promotion, and only then: 

PUT <base>/_cell_writers/v1/<cell_id>
    {"node_id":"graph-node-1","epoch":18,"at":"2026-07-25T14:32:07Z"}

Read on exactly two paths, both off the write path: when logging a CloseReason::Fenced, and when building the NotCellWriter { owner } hint. Never consulted to decide whether to promote — that is rendezvous' job, and consulting it would be a read-then-act race that adds a GET to the write path and looks like it works.

What it buys is the diagnostic half of the incident. The same production trace becomes: 

node-0  WARN  fenced at epoch 17; current lease: graph-node-1 @ 18
node-1  WARN  fenced at epoch 18; current lease: graph-node-2 @ 19

Nothing is prevented. But the ping-pong is visible in one line instead of inferred across three logs, the NotALeader hint carries an observed owner rather than a computed guess, and after the fact you can answer "who actually had it at 14:32" from object storage.

The SlateDB writer epoch remains the only authority. The record can be stale — a node can be fenced a millisecond after writing it. It answers "who last successfully promoted", not "who holds the writer right now". If it ever disagrees with the manifest, the manifest is right.

Q1, finalised — docs/plans/2026-07-25-rendezvous-placement-open-questions.md:493–498

The genuinely authoritative option — adding an expected_writer_epoch compare-and-set to Db::builder so that build() fails instead of fencing — was scoped and then dropped. It is buildable, since the dependency is our fork. But sleet demonstrates the bound is achievable without it, our check is stricter than sleet's, and it would gate a production fix on a dependency change that alters the fencing contract architecture.md rests on. The prod incident's actual pain was diagnostic, not a correctness failure; the advisory record fixes precisely that and nothing else claims to.

H — state of play

What is decided, what has landed, what is still open

Landed

crate crates/placement, package turbolay-placement, publish = false. No dependencies; the frozen hash is pure functions over &str. No dependency on slatedb-graph-kernel either — placement must not know about graphs, shards or queries.

Decided

Q1 lease Advisory record only. _cell_writers/v1/<cell_id>, written after a successful promotion, read only for logging and the owner hint. CAS-on-open dropped.
Q3 timings heartbeat_interval 5s, heartbeat_timeout 15s. Config, with startup validation that interval < timeout. The fence backoff in touch point (d) is one interval, so 5s.
Q2 readyz Delete the client-side fan-out. reachable_nodes, probe_node_readiness, replace_address_port and the reachable.first() writer fallback all go — replaced by one LIST, with heartbeat publication gated on AdminState.ready. fence Match sleet's handler exactly (daemon.rs:458-472): reset backoff to 1s because a fence is view skew rather than a failure, wait exactly one heartbeat_interval sized to let the rival stand down, and retry unconditionally without re-checking ownership.
LIST failure Bounded, then shed. Keep the last good view while it is younger than heartbeat_timeout, then go unready, DELETE the heartbeat and refuse promotion. The grace equals the timeout because peers take over that long after the last successful PUT — shorter leaves a window with no owner, longer leaves a duel, equal makes them coincide. Withdrawing the heartbeat is what closes the partial-failure case where LIST is throttled but PUTs still land. Worst case for the cell is 30s, against sleet's unbounded.
Q4 scope All of Phase 1, one release, as seven staged commits: crate → publisher → (a) routing → (b)+(c) refusal and mapping → (d) fence backoff → 3a record → regression test. The publisher splits out of (e) and lands before (a), because (a) deletes the probe and cannot function until heartbeats exist. Commits 3 and 4 must not be separated.
rolling restart directory.rs distinguishes never-published from expired: for the first heartbeat_timeout after start, a configured peer with no heartbeat object counts as live. Only expiry is evidence of death. Without this, the first pod replaced in a rolling restart LISTs, sees only itself, and concludes it owns every cell.

Does with_preferred_writer_node survive? open

The recommendation reversed on reading the code. It has no production caller at all: graph-node.rs:115-116 builds the provider and never calls it, so the field is always its default — the lexicographically first key of a BTreeMap (routing.rs:76-80). Its only caller in the tree is bolt/tests.rs:1373. Both arguments for keeping it were also wrong: single-node deploys have nothing to override, since rendezvous over one live node has exactly one answer; and a test should compute the owner rather than pin it, which is what the heartbeat widget above already does.

Worse, keeping it becomes unsafe the moment (b) enforces ownership. Routing would advertise the override while ensure_local_writer enforces rendezvous, so a driver sent to the override is refused, re-routes to the rendezvous owner, and is sent back by the next ROUTE refresh — a loop no timeout breaks, from a misconfiguration that validates cleanly. Today the same field is harmless only because nothing enforces ownership. Recommendation is to delete it; if a pin is ever wanted it belongs inside owner() so both sides read one source.

Rebalance dampening, cell splitting, multi-cell atomicity

All explicitly out of scope, all still real. Rendezvous moves ownership the instant the live set changes; if flapping hurts, a minimum-tenure rule is the answer, not a longer timeout. Cells come from GRAPH_CELLS and are static, so routing a hot cell correctly to one writer is exactly what makes it a bottleneck. And Phase 2 — letting a write name its cell on the wire — is the change that makes multi-cell atomicity urgent rather than theoretical.

summary

Three moving parts, and one claim that has to stay honest

A frozen hash gives every node the same answer to "who owns this cell", computed from an object-store LIST and nothing else. One branch in ensure_local_writer makes that answer binding, and a Bolt error code lets the driver act on the refusal. Heartbeats replace a per-request probe fan-out with a single consistent liveness view, at the price of a 15-second write stall on a hard crash of the owning node.

None of it prevents two nodes from briefly believing they both own a cell. SlateDB's writer epoch remains the only mutual-exclusion mechanism, exactly as architecture.md requires. What changes is that the disagreement now has a deadline: it lasts as long as two views of the live set differ, and no longer. Unbounded becomes fifteen seconds. That is the whole trade, and it is worth making.
