One cell, one writerand no way to say which node that is

SlateDB gives every cell a fenced single writer. Turbolay never decides who that writer should be — it lets whichever node received the request take the epoch. This is a survey of what breaks as a result, and what a correct router would have to provide.

A — the invariant

Fencing is a rejection mechanism, not an election

Everything downstream follows from this one distinction, so it is worth stating precisely before anything else.

A cell is an independent SlateDB database. The object-store layout puts each one under its own prefix, with its own manifests, WAL, compacted SSTs, and index generations:

path segmentowns
namespaces/<tenant>/…tenant and up to seven nested subnamespaces
graphs/<graph-id>/the graph selected inside that namespace path
<cell-id>/one SlateDB database — independent WAL, snapshots, writer fencing, indexes, cache locality

architecture.md:334–356

SlateDB enforces one writer per database. A process becomes the writer by opening the database, which claims a newer writer epoch with an object-store compare-and-swap and installs a WAL barrier. Any older writer is fenced: its subsequent commits fail.

That is a strong safety property and a weak coordination property. Nothing prevents a second process from opening the database — the fence only tells the loser, and only afterwards. SlateDB will happily let ten nodes take turns being the writer for one cell, forever, with perfect durability and no data loss.

Every namespace, graph, and cell has one active SlateDB writer and any number of SlateDB readers.

A preferred writer address is cache affinity, not correctness authority.

architecture.md:16, :21 — design invariants

The second line is the load-bearing one, and it is correct as written. The router is deliberately not in the safety path. But a router that is not authoritative still has to be good — and today there effectively isn't one.

B — a write, traced

Where the cell is decided, and where it isn't

Following a single CREATE from the Bolt socket to the WAL commit. The marked step is where the current design commits to an outcome that routing was supposed to prevent.

01

Driver picks a node from its cached routing table

The Neo4j driver holds the last ROUTE response for its TTL — 30 seconds as configured. It sends the write to whatever single address sat under the WRITE role.

src/bin/graph-node.rs:115

02

Database name resolves to a scope — but not to a cell

HierarchicalClientDatabaseResolver decodes <base>.scope1.<b64-tenant>.<b64-subtenant> into a namespace path and a graph id. Then it fills in the cell by copying self.root_target.cell_id — a constant read from GRAPH_CELL_ID at process start.

src/client/service.rs:112–116 · src/bin/graph_node/config.rs:19,76

03

The statement is classified read or write

classify_opencypher_query_access decides before authorization. A write proceeds to ensure_local_writer(&context.cell_id).

src/engine/cluster.rs:683–689

04

The node makes itself the writer — unconditionally

ensure_local_writer checks exactly two things: that this process is promotable, and that it holds a shard for the cell. It never asks whether it should be the writer. It calls promote_to_writer.

src/engine/cluster.rs:375–390

05

Promotion is a full SlateDB writer open, on the request path

GraphStore::promote_writer calls open_graph_db(...) — manifest read, epoch CAS, WAL recovery, cold memtable. Synchronously, inside the first write that needed it.

src/core/state.rs:248–270

06

Whoever held the epoch is fenced

The previous writer — possibly a healthy node with a warm cache mid-batch — discovers this on its next refresh_writer_fence, gets CloseReason::Fenced, and drops its handle.

src/core/state.rs:235–246

07

Commit, and a durable bookmark returns

This part is sound. Successful return means the mutation reached SlateDB's durable commit point.

architecture.md:258–259

Steps 04 and 05 are the whole problem in two calls. There is no point in this path where any component consults, computes, or records an answer to “which node should be the writer for this cell?” Ownership is a side effect of having received a request.

C — the routing table today

One WRITE address for the entire cluster

ObjectStoreBoltRoutingTableProvider is the only routing implementation wired into the node binary. Its signature is the tell:

parameterused?what it could have meant
_databasediscardedthe tenant scope whose cells we are routing for
_targetdiscardedthe ClientQueryTarget, which already carries scope and cell_id

src/client/bolt/routing.rs:222–226 — the arguments needed to route per cell are already delivered to the function that ignores them.

What it returns instead: every node it could reach over a 250 ms /readyz probe, with a single writer picked by a fixed preference.

roleaddressesselection
ROUTEall reachableevery node that answered the probe
READall reachablecorrect — every ready node can serve every cell
WRITEexactly onepreferred_writer_node if reachable, else reachable.first(). The default preference is whichever node id sorts first in a BTreeMap.

src/client/bolt/routing.rs:76–80, 235–249

So writes for every cell in every tenant scope land on one node. Cells exist precisely to give a graph independent WALs, independent snapshots, and independent fencing domains — and the routing layer collapses all of them back onto a single writer process.

D — failure modes

Ten things that follow from having no owner

Ordered by severity, not by sequence. Severity here means how much of the design goal it defeats — none of these are data-loss bugs, because SlateDB's fence holds throughout.

F-01

Cells are not addressable on the wire

critical

The Bolt and HTTP protocols carry a database name. The hierarchical resolver maps that name to a tenant namespace and a graph id, and then hardcodes the cell from node configuration. A client physically cannot say which cell its write belongs to. StaticClientDatabaseResolver can map database→cell, but only through a hand-maintained table, and still cannot express “this write belongs to cell X because of its key.”

Consequence: routing cannot be made correct, because there is nothing to route on. Every other fix depends on this one.
F-02

Write throughput is capped at one node, regardless of cell count

critical

The routing table has one WRITE role for the whole database. Adding cells adds parallel WALs, parallel snapshots, and parallel fencing domains — and adds no write capacity at all, because they all resolve to the same address.

Consequence: the primary architectural benefit of cells is unspent. Scaling writes means scaling one process vertically.
F-03

Ownership is self-asserted and unrecorded

critical

No node ever asks whether it owns a cell. ensure_local_writer promotes on demand. There is no ownership record in object storage, no lease, no directory entry, no computable placement function. The system has no way — even offline, even for an operator — to answer “who is the writer for cell-2?” other than by observing which node last succeeded.

Consequence: ownership is unobservable, so it is also untestable and unschedulable.
F-04

A fenced write has no protocol answer

high

Bolt has a native mechanism for exactly this condition: Neo.ClientError.Cluster.NotALeader tells a driver to discard its routing table and re-route. Turbolay emits no such code — the entire Bolt module contains one error code, Neo.TransientError.Transaction.Terminated, for deadline expiry. A fenced write surfaces as an opaque error and the driver retries into the same wrong node.

src/client/bolt.rs:1366 — the only Neo error code in the file

Consequence: the client cannot participate in its own correction. This is the highest value-per-line gap in the system.
F-05

Promotion duels have no convergence bound

high

Two nodes with different routing views — a 30-second TTL, independently timed probes, per-driver caching — can alternately promote, each fencing the other. Neither is misbehaving. Nothing makes a fenced node stand down, because nothing told it to stand up. There is no reason for the oscillation to stop on its own.

Consequence: a livelock that is perfectly safe and completely unproductive. See section E.
F-06

Promotion cost is paid on the request path, per duel round

high

promote_writer is a full Db::builder(..).build(): manifest read, epoch CAS against object storage, WAL recovery, fresh memtable, cold block cache. It runs inside the first write that needs it. Under F-05, this cost multiplies by the number of duel rounds.

Consequence: failover latency and duel latency are the same number, and it is an object-store round-trip class number.
F-07

The routing provider is cell-blind by signature

high

routing_table(&self, _database, _target) receives everything it would need and consults none of it — not because of an oversight in the call, but because there is no per-cell ownership map anywhere in the system for it to consult.

Consequence: the fix is not in this function. The function is waiting on a placement decision that does not exist yet.
F-08

Readiness is being used as a proxy for ownership

medium

Advertisement is gated on a TCP connect plus GET /readyz returning 200 within 250 ms. A node can be ready and not the writer; a node can be the writer and briefly miss a probe. The probe also fans out to every node on every ROUTE request, so liveness is computed per-caller and can disagree between two clients asking at the same moment.

src/client/bolt/routing.rs:152–168, 196–218

Consequence: N TCP connections per routing refresh, and an inconsistent liveness view feeding an already-ambiguous decision.
F-09

Writer-capable handles are unbounded in the cell dimension

medium

Cache and memory budgets are partitioned across scopes — object_store_cache_bytes / max_open_scopes, per-scope cache directories. Nothing performs the equivalent bounding for writer handles, which scale as cells × nodes.

src/engine/cluster.rs:830–845 (scope budgets) vs :293–329 (unbounded shard opens)

Consequence: the memory story is scope-aware and the writer story is not.
F-10

Multi-cell writes have no story at all

medium

A write touching two cells is two independent SlateDB transactions producing two bookmarks with no relationship. Reads have a fan-out — execute_cypher_rows_many iterates cells sequentially — but there is no write equivalent and no cross-cell atomicity.

src/engine/cluster.rs:719–741

Consequence: once cells become independently routable, this becomes the next question immediately. It is worth deciding the answer before, not after.

E — safe but not live

The promotion duel, step by step

F-05 deserves its own walkthrough, because it is the failure that most people assume SlateDB's fence already prevents. It doesn't — the fence guarantees that the duel is harmless, not that it ends.

t + 0s

Driver A holds a routing table naming node-0 for WRITE.
node-0 holds epoch 17, warm.

t + 3s

node-0 misses one 250 ms probe under load. Driver B refreshes and gets node-1 for WRITE.

t + 4s

B writes to node-1. node-1 promotes: epoch 18.
node-0 is fenced.

t + 6s

A's cached table is still valid for 27 more seconds. A writes to node-0. node-0 promotes: epoch 19.
node-1 is fenced.

t + 9s

B writes again to node-1. Epoch 20.
node-0 fenced. Both caches cold. Repeat.

Every commit in that sequence is durable and correctly ordered. No write is lost, no read is stale, no invariant is violated. And yet each round costs a full writer open, a cold memtable, and a discarded block cache on both nodes.

This exact hazard is named and bounded in sleet, the sibling design on the same storage primitives:

A running coordinator can be fenced by a newer compactor_epoch. Sleet treats that as evidence of view skew. The fenced task waits one heartbeat_interval, then reruns … Mutual fencing can last only while the two nodes disagree about ownership, which is bounded by config_poll plus one heartbeat tick.

sleet — rfcs/0001-design.md, “Coordinator fencing”

Two things make that bound work, and Turbolay has neither. First, sleet nodes compute ownership, so a fenced node can ask whether it still believes it owns the work. Second, they back off deliberately, giving the rival the same chance to stand down. A Turbolay node that gets fenced has nothing to consult and no reason to wait — the next request that arrives will make it promote again.

F — requirements

What a correct router has to provide

Stated as constraints on any solution, so that the options in the companion document can be scored against something.

R1 A write must be able to name its cell, derived from the request rather than from node configuration. blocks F-01, F-02; prerequisite for every other requirement
R2 Any node must be able to answer “who owns cell X?” without asking a consensus service. blocks F-03, F-07
R3 Ownership must be stable enough that the node with the warm writer usually receives the write. this is what makes routing worth having at all — see architecture.md:21
R4 A write that arrives at the wrong node must be corrected, not absorbed. blocks F-04; the node must decline or forward rather than steal the epoch
R5 Correction must converge within a stated bound. blocks F-05, F-06; sleet's bound is config_poll + one heartbeat tick
R6 Safety must continue to rest solely on the SlateDB writer epoch and WAL barrier. If placement is wrong, writes stay correct and only get slower. architecture.md:20–21 — non-negotiable
R7 No new consensus service and no writable controller in the data path. architecture.md:26–27; sleet RFC-0001 non-goals

R6 and R7 together are what make this genuinely hard, and what makes most of the distributed-systems literature inapplicable off the shelf. The usual answer to R2 is a placement authority — etcd, ZooKeeper, or a purpose-built driver. Both of those are ruled out here by design, not by expedience.
