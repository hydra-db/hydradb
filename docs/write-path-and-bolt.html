Part 1 · Which shard does a write go to?

There is no hash-based routing on writes. A write is explicitly addressed by (scope, cell_id). The caller carries the shard identity; the server does an exact-string map lookup — never a hash of the payload.

Do all writes to the same tenant / sub-tenant hit the same shard?

Cross-scope traffic is rejected outright by ensure_query_scope. cluster.rs:743

Consequence. Multi-cell fan-out exists in the engine but is unreachable over Bolt. Set GRAPH_CELLS=cell-0,cell-1 and both SlateDBs open — but the Bolt resolver only ever emits root_target.cell_id, so cell-1 gets zero writes. Only HTTP (cell_id is a body field, http.rs:284) and the direct Rust API can address a second cell. A tenant's write ceiling is currently one shard's throughput. Splitting a hot tenant across cells needs a routing function (e.g. hash(src) % cells) that doesn't exist yet — and it isn't free: cells are independent SlateDBs with independent fences, so an edge whose endpoints hash to different cells has no atomic home. The design sidesteps this by making the tenant the unit of sharding.

Key takeaway. Bolt never routes by data. It resolves the database name to (scope, cell_id), classifies the query as read or write by parsing it, then either takes a lock-free reader snapshot or promotes the single fenced SlateDB writer for that one cell. Sharding is entirely a function of which database (tenant) you connected to.
