# M0 Implementation Handoff

Short handoff for whoever writes the first turbolay code. **No code exists yet** — the RFC set (`docs/rfcs/`, all 10 drafted) is the spec; this is the on-ramp. Read `2026-07-03-references-and-source-map.md` first for where everything lives.

## What M0 is

The storage foundation: **keyspace + order-preserving encoding + UID/xid allocation**, on `opendata/common`, with property tests. No graph semantics yet, no query — just "we can encode/decode every key and value correctly and allocate ids crash-safely." Exit = RFC 0003 acceptance tests green.

**Binding specs:** RFC 0003 (keyspace/encoding) and RFC 0004 §UID allocation. Everything else (0005 postings, 0006 indexes, 0007 query, 0008 service) is M1+.

## First decisions already made (don't re-litigate)
- Reuse `opendata/common` (D8) — depend on it or vendor `common/src/serde/` + `common/src/storage/`. **First task: confirm `opendata` is reachable as a path/git dep from this repo; if not, vendor `serde/` + `storage/` + `sequence.rs`.**
- Subsystem byte `GRAPH = 0x05` (add to `common::serde::subsystem`).
- Keys big-endian, values little-endian; `bytes::Bytes` everywhere; `cargo fmt` + clippy `-D warnings`; tests given/when/then + `should_`.

## Suggested crate/module layout (mirror opendata `log/`)
```
turbolay/
  Cargo.toml            # deps: slatedb 0.14.1, opendata-common (path/git or vendored), roaring, bincode, bytes, tokio, proptest(dev)
  src/
    lib.rs              # pub re-exports
    serde/              # M0 CORE — the keyspace (RFC 0003)
      mod.rs
      record_tag.rs     # RecordType enum: SchemaName/SchemaId/Node/EdgeOut/EdgeIn/EdgePart/Index/Count/Xid/Log/Meta
      keys.rs           # key builders + parsers per record type (the inverse pairs)
      value.rs          # NodeRecord, PostingValue(roaring) stubs, ChangeRecord (encode/decode)
    ids.rs              # UID + schema-id allocation over common::SequenceAllocator; xid->uid resolution
    schema.rs           # in-memory schema cache (name<->u32 id) backed by SchemaName/SchemaId records
    storage.rs          # thin wrapper over common::Storage (GraphStorage / GraphStorageRead)
    error.rs config.rs
```

## M0 deliverables (in order)
1. **`serde/record_tag.rs`** — `RecordType` + `RecordTag` (high-nibble), round-trip.
2. **`serde/keys.rs`** — for each record type: a `build(...) -> Bytes` and a `parse(&[u8]) -> ParsedKey` that is its exact inverse. Use `common::serde::{KeyPrefix, terminated_bytes, sortable}` for components; UIDs/ids big-endian fixed-width; changelog seq fixed-BE u64.
3. **`ids.rs`** — UID allocator + schema-id allocators over `SequenceAllocator`; `resolve_or_create(xid)`; recovery (`load` resumes at `base + block_size`).
4. **`schema.rs`** — intern label/predicate/property names to u32, write `SchemaName`/`SchemaId` in the same batch, cache in memory, rebuild cache on open.
5. **`storage.rs`** — open a `common::Storage` via `StorageBuilder` (InMemory for tests), register the merge operator stub (RFC 0003 dispatch), `apply`/`get`/`scan_prefix` helpers.

## First failing test to write (do this first)
A proptest asserting **`encoded byte order == logical order`** for the composite `Index[pred_id][token]` key across `int`/`float`/`exact` tokens and boundaries (0, negatives, ±0.0, u64::MAX, embedded 0x00, `"a"` vs `"ab"`). It fails until `keys.rs` + `sortable`/`terminated_bytes` wiring is right. This is the M0 north star (RFC 0003 Acceptance #1–6).

## How to run/test
- Unit + property tests use `common::InMemoryStorage` or `object_store::memory::InMemory` — **no S3, no LocalStack** for correctness.
- Real S3 is bench/integration only (RFC 0017 D12) — never LocalStack for perf numbers.
- `#[opendata_macros::storage_test]` injects a storage handle; copy opendata's test patterns.

## Gotchas
- SlateDB is pre-1.0: pin `slatedb = "0.14.1"`; keep it behind `common::Storage`, never call `slatedb::Db` directly.
- The merge operator must be registered on the writer **and every `DbReader`/compactor** or reads of merge operands fail `MergeOperatorMissing`.
- Dense u64 UIDs are load-bearing (roaring efficiency) — do NOT use UUIDs as internal ids (namidb's documented mistake).
- Roaring `RoaringTreemap` (64-bit) is the posting representation (RFC 0005) — pick the crate + a stable serialization format early (note in scratchpad).

## After M0
M1 = write path + posting lists (RFC 0004/0005); M2 = indexes + read consistency (RFC 0006/0001); M3 = Cypher read + service (RFC 0007/0008). See `2026-07-03-implementation-plan.md`.
