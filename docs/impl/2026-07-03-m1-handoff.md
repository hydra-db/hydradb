# M1 Implementation Handoff

On-ramp for whoever writes the **write path + posting lists**. **M0 is done and green** (keyspace, encodings, id allocation — see `2026-07-03-m0-handoff.md` for what it was and the scratchpad for what shipped). This doc is what you build on top of it. Read `2026-07-03-references-and-source-map.md` for where the external repos live.

**Binding specs:** RFC 0004 (data model, write path, UID allocation, logical-seq protocol) and RFC 0005 (posting-list substrate — roaring). RFC 0003 (keyspace) is the layer beneath you and is finished.

## What M1 is

Turn the M0 keyspace into a **writable graph**. A write request (`UpsertNode` / `UpsertEdge` / `DeleteNode` / `DeleteEdge`) lowers into **one atomic `WriteBatch`** — node record + both edge projections + affected posting lists + changelog + `m/latest_seq` — committed at a single SlateDB seq. The value at every adjacency/index key becomes a **roaring posting list** with add/delete/split/rollup lifecycle. No query yet (that's M3); no secondary indexes yet (that's M2 — but the posting-list machinery you build here is what M2 reuses).

**Exit = RFC 0004 acceptance (1–6) + RFC 0005 acceptance (1–6) green.** The headline tests: crash-recovery mid-batch, zombie-writer fencing, atomic fan-out in one seq, tombstone-and-filter delete correctness, and set-algebra-vs-`BTreeSet`-oracle.

## First decisions already made (don't re-litigate)
- **Roaring** for all posting values (Q2, RFC 0005): adjacency sets, index sets, deleted-node/deleted-edge bitmaps — one type everywhere. `RoaringTreemap` (64-bit). CSR/UidPack stay deferred behind the `format` tag.
- **Node record = monolithic bincode blob** behind a `NodeCodec` trait (Q6/Q7). rkyv is a fast-follow spike only if node reads show up in profiles — keep it behind the trait.
- **Tombstone-and-filter deletes** (Q8/Q9): `DeleteNode` unions into `Meta["deleted_nodes"]`; `DeleteEdge` unions into `Meta["deleted_edges"/pred/anchor]`. O(1), degree-independent. Physical purge is vacuum (RFC 0012, not M1).
- **Size-adaptive add** (Q10): merge-union into a `Single` list on the hot path; single-writer RMW to bin-split at **512 KiB**.
- **Bidirectional storage unconditional** (D10): every edge writes `EdgeOut` and `EdgeIn` in the same batch.
- **One atomic `WriteBatch` per request**, `await_durable: true`, ack with the session token (logical seq).

## Deliverables (in order)

1. **`src/posting.rs` — `PostingValue`** (RFC 0005 §"Posting value format"). `{ format: u8 = 1, kind: Single|Split, set: RoaringTreemap | parts: Vec<PartRef{start,min,max,card}> }`. Serialize/deserialize (roaring's portable format + your header). This is the *first* thing to build and the first thing to test (set-algebra-vs-oracle proptest — see below). M2 reuses it verbatim for index posting lists.
2. **`src/value.rs` — `NodeRecord` + `NodeCodec` + `ChangeRecord` + `TypedValue`** (RFC 0004 §"Node record", §"ChangeRecord schema"). bincode default; enforce the **1 MiB node-size cap** (reject `oversize_node`). `TypedValue = Null|Bool|Int(i64)|Float(f64)|String|Bytes|DateTime`.
3. **Fill `src/merge.rs`** — implement the RFC 0003 dispatch table the stub documents: roaring `Treemap` **union** for `EdgeOut`/`EdgeIn` fast-add and the deleted-node/deleted-edge `Meta` bitmaps; **i64 LE sum** for counter `Meta` keys; **fail-closed** (return newest + `tracing::error!`, or panic per your call) for the non-associative rows (`Index`/`Count`/`Node`/`Schema*`/`Xid`/`Log` must never receive a merge operand). Route on `serde::keys::record_type_of(key)`.
4. **`src/posting_ops.rs` (or fold into `posting.rs`) — add / delete / split / rollup** (RFC 0005 §"Add/delete mechanics"). `add` = size-adaptive (merge-union small, RMW split at 512 KiB); `delete` = merge into the deleted bitmap; `neighbors(anchor,pred,dir,&deleted_nodes)` = read (Single, or manifest+parts) then subtract deleted-edge and deleted-node bitmaps; `rollup` = fold deleted into set when deleted-card > 25% of live.
5. **`src/write.rs` — the write path** (RFC 0004 §"Write path"). `UpsertNode`/`UpsertEdge`/`DeleteNode`/`DeleteEdge` → `Vec<RecordOp>` → `GraphStorage::apply` at one seq. Each op appends `Log[seq]` + `Meta["latest_seq"]` and returns the session token. Reuse `GraphAllocators` (persist block records **in the batch**) and `SchemaCache` (intern new names, add `SchemaName`/`SchemaId` to the batch).
6. **Recovery on open** (RFC 0004 §"Logical sequence protocol"): read `Meta["latest_seq"]`, resume `next_seq`, `GraphAllocators::load`, `SchemaCache::rebuild_from_storage`. A mid-flight batch either fully committed (SlateDB WAL) or didn't.

## Two integration points that will bite you

**#1 — `resolve_or_create_xid` must move into the batch.** The M0 version (`ids.rs`) persists the `Xid → uid` mapping with its own `storage.put` — fine for M0's smoke path, wrong for RFC 0004, which requires the mapping + node record + seq-block record to commit **atomically with the rest of the write**. Refactor to a function that *returns* the `RecordOp`s (xid mapping, any seq-block record) for the caller to fold into the request batch, instead of writing them itself. Keep the eager version only if something still needs it; the write path must use the batch version.

**#2 — logical-seq injection (`WriteOptions.seqnum`) is NOT in the `common` API yet.** RFC 0004 commits each batch with `WriteOptions { await_durable: true, seqnum: latest_seq }` so turbolay's logical seq == SlateDB's durable seq (which the RFC 0001 reader gate polls via `subscribe_durable`). But `common::WriteOptions` today exposes **only `await_durable`** — there is no seqnum passthrough to SlateDB. You must either (a) extend `common`'s `WriteOptions` + `SlateDbStorage` adapter to forward an injected seqnum to `slatedb::WriteOptions.seqnum` (preferred — keeps logical and durable seq identical, the RFC's design), or (b) decouple: keep the logical seq only in `Meta["latest_seq"]` and build the reader gate to map token→durable itself. Decide this **before** writing `write.rs`; it shapes the token/gate contract. This is the top standing risk in the scratchpad ("`WriteOptions.seqnum` injection" spike).

## Roaring spike — do this before deliverable #1

The scratchpad flags it and it's load-bearing: pick the `roaring` crate (opendata's workspace pins `roaring = "0.10"` — match it), add it to `Cargo.toml`, and **confirm `RoaringTreemap` portable serialize/deserialize is stable and cheap**, and measure serialized size vs a UidPack-style baseline on realistic adjacency (validates Q2). Note the chosen serialization format in RFC 0005. Roaring is deliberately **not yet a dependency** (M0 needed none) — you add it.

## First test to write (do this first)

A **set-algebra-vs-oracle proptest** (RFC 0005 acceptance #2): generate random `Vec<u64>` inputs, build `PostingValue`s and a naïve `BTreeSet<u64>` oracle, and assert AND/OR/NOT/difference/cardinality/min/max agree. It fails until `PostingValue` (deliverable #1) round-trips and wraps roaring correctly, and it's the M1 north star the same way the `Index[pred][token]` ordering test was M0's. Then force the split threshold low and assert the split lifecycle (acceptance #3): a growing list splits, manifest min/max/card are correct, and whole-set + range-filtered reads match the unsplit oracle.

## How to run/test
- Correctness on `common::storage::in_memory::InMemoryStorage` or `object_store::memory` — **no S3, no LocalStack** (RFC 0017 D12; LocalStack hid namidb's ~10× cold regression).
- Crash-recovery / fencing tests: use SlateDB fault injection (`common::FailingStorage::fail_apply` per RFC 0004 acceptance #1; confirm the exact helper name in `common`) and a second-writer open for `CloseReason::Fenced`.
- Real S3 is bench/integration only, and it's the RFC 0017 gate before any optimization RFC.

## Gotchas
- **Register the merge operator on readers/compactors too.** `GraphStorage::open` registers it on the writer. When M2 adds a `DbReader`, it must build with the *same* `GraphMergeOperator` or reads of merge operands fail. (`common::create_storage_read` takes `StorageSemantics` — pass it there.)
- **Split/rollup are single-writer RMW, never merge** — they're non-associative. Only union/counter-sum go through the merge operator. Getting this wrong corrupts posting lists silently.
- **Never one S3 object per edge.** Edges live *inside* posting lists inside SlateDB SSTs. Design against tombstone storms + tiny-object storms (fundamentals ch18).
- **Dense u64 uids are load-bearing** — the allocators already guarantee this; don't smuggle in a non-dense id anywhere.
- **`await_durable: true` on the write batch** — the session token must be durable before you ack (RFC 0001 read-your-writes).
- **Node cap is the *node* record (1 MiB); adjacency is bounded by the 512 KiB posting split** — two different limits, don't conflate.

## Acceptance checklist (copy from the RFCs)
RFC 0004: (1) crash-recovery mid-batch, (2) zombie-writer fencing continues seq lineage, (3) read-your-writes across a `DbReader` with a token, (4) delete filters tombstoned uid both directions + count reflects it, (5) xid stability + uid monotonicity across a half-used-block restart, (6) atomic fan-out in exactly one SlateDB seq.
RFC 0005: (1) `PostingValue` round-trip + ascending-uid iteration, (2) set-algebra vs `BTreeSet` oracle, (3) split lifecycle from day one, (4) delete correctness + rollup folds bitmap, (5) supernode add touches one part not the whole set, (6) facet companion `EdgeProp` record.

## After M1
M2 = index framework + value/reverse/count indexes + read consistency (RFC 0006/0001) — reuses your `PostingValue` and the changelog-tail this milestone writes. M3 = openCypher read subset + HTTP fleet (RFC 0007/0008). See `2026-07-03-implementation-plan.md`.
