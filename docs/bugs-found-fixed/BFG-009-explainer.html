BFG-009 — epoch-scoped reads compose over unpinned live state

An epoch-scoped read is not a pure function of its epoch. Later writes rewrite the answer to an earlier question, so an acknowledged delete can be retroactively erased and a read can return data committed after its own epoch.

The bug itself

The visibility rule for segment adjacency is segment.storage_sequence <= read_epoch, with a tombstone applying when tombstone_epoch <= read_epoch. That rule is only sound when evaluated against storage state pinned at read_epoch. Several read paths evaluate it against live — or later-pinned — state instead.

Two writer behaviors then destroy the history the rule depends on:

  1. Segment re-append deletes the tombstone key of a prior acknowledged delete (src/shard/write.rs:4279). Correct for current reads; it erases the only record that an epoch-scoped evaluation over newer state would need.
  2. The point-edge branch has no epoch filter at all (src/engine/artifact_build.rs:497-506, same shape in out_neighbors_in_storage_snapshot at src/shard/query.rs:135-142).

Composition of the two: the same call, with the same epoch argument, returns different answers depending on what has been written since.

One writer cycles acknowledged delete_edge / segment re-append on a single edge, recording each acknowledged (epoch, state) pair. A reader derives current_epoch() and immediately reads at it — the exact query_read_epoch-then-read composition the kernel-page fallback uses (query.rs:4495 → query.rs:4894, with no seq == read_epoch guard between them).

681 current-epoch reads contradicted acknowledged history; first:
(read_epoch, expected, observed) = Some((6, false, true))

681 of 4000 reads — 17%. A read anchored at epoch 6 observed an edge whose delete was acknowledged at epoch 6. In Jepsen terms: a read-your-writes violation for the deleting session, and a set-full resurrection (present → acknowledged-absent → present).

Root cause

edges_at → canonical_adjacency_at → current_matrix_rows (src/engine/artifact_build.rs:488-532) performs three separate live prefix scans — point edges unfiltered, tombstones and segments epoch-filtered — with no snapshot pinning at all when called outside scope_snapshot.

Meanwhile segment re-append deletes tombstone keys (write.rs:4279), and segment compaction deletes tombstones and rewrites segment sequences (maintenance.rs:207-229). Both are correct for current reads. Both erase the record that epoch-scoped evaluation over newer state requires. The _at APIs promise history the storage layer deliberately does not keep.

Blast radius — and what is safe

Safe

The main cypher rows path, execute_parsed_opencypher_rows (src/shard/query.rs:461-476), pins one snapshot via scope_snapshot and derives read_epoch from that snapshot, so its live scans resolve against pinned state. Indexer builds are likewise consistent: build_graph_index runs canonical_adjacency_at(base_sequence) inside scope_snapshot at base_sequence == snapshot.seq(), neutralizing both unpinned branches.

  • The _at APIs — the direct expression of repros 1 and 2.
  • Kernel / streaming page fast paths (query.rs:4475, :4607) derive read_epoch from a dropped snapshot, and their storage fallback takes its own fresh snapshot (reachable_from_storage_frontier, query.rs:4894) with no seq == read_epoch guard. Any delete-plus-re-append committing between those two lines tears the composition inside a single page. The compiled path does guard (seq() != read_epoch → fallback, query.rs:5268) — but the fallback it lands on is the unguarded one.
  • validate_cell_edge_type (query.rs:6059) reads current_epoch then edges_at unpinned; its repair report can claim false degree mismatches.

Checked and ruled out

  • Forced-sequence commits — commit_txn_strict pins the commit sequence to seqnum()+1 (src/codec.rs:143-159), so epochs equal real commit sequences. Not the cause.
  • Segment scan early break — segment keys zero-pad the sequence (src/keys.rs:67-74), so lexicographic order is numeric order.
  • Segment compaction atomicity — atomic, and preserves out-of-range tombstones and live-at-epoch semantics (maintenance.rs:189-248).
  • DETACH DELETE coverage — scans segments as well as point edges (write.rs:739-773).

Fix directions (none applied)

  1. Pin or reject. Pin every epoch-scoped read to a storage snapshot whose seq() == read_epoch, or reject with SnapshotAhead / UnsupportedQuery the way snapshot_at already does (src/shard/lifecycle.rs:620-639). This is the cheap fix.
  2. Derive the epoch from the snapshot you traverse. In the kernel and streaming page paths, take the snapshot first and use its seq(), mirroring execute_parsed_opencypher_rows.
  3. Stop destroying history — only if historical epoch answers are a genuine product requirement. Tombstone keys must not be deleted on re-append (write a supersede record instead), and point edges need an epoch-carrying record. Much larger change; 1+2 restores correctness without it.

The Quint module, now written

Three files in the M2 family, following the existing convention.

m2_epoch_scoped_read.qnt — the intended contract. Every append, point write, and tombstone is retained as a set, so any epoch can be reconstructed. Three invariants:

  • epochScopedReadIsStable — re-reading an already-answered epoch gives the same answer, however many commits landed at later epochs.
  • readNeverSeesTheFuture — the answer equals the state reconstructed at the read epoch.
  • readMatchesAcknowledgedHistory — a read anchored at an acknowledged epoch agrees with that acknowledgement.
quint run m2_epoch_scoped_read.qnt --invariant=allSafety \
  --max-steps=16 --max-samples=50000
[ok] No violation found (328ms at 152439 traces/second)

All four witnesses — deleteAcknowledgedReached, reappendAfterDeleteReached, rereadAfterReappendReached, pointEdgeAfterReadReached — are reachable, so nothing holds vacuously.

m2_epoch_scoped_read_buggy.qnt — the fault model. Encodes the two implementation behaviors: the re-append deleting preceding tombstones (write.rs:4279), and the point-edge branch with no epoch filter (artifact_build.rs:497-506). It violates two of the three invariants — epochScopedReadIsStable and readNeverSeesTheFuture — which is what proves those two discriminate this bug rather than passing on anything.

The third, readMatchesAcknowledgedHistory, is not discriminated — and that is a stated limit of the module, not a weakness in the e2e evidence. A read is atomic here: the epoch is derived and evaluated in one action, so observedAt == ackedEpoch is only ever tested against the state that produced the acknowledgement. Repro 3 fails for exactly the reason this model cannot express — query_read_epoch and the read are separate steps with a writer committing between them. Discriminating it formally needs a two-action-read module, which does not exist yet.

The shortest counterexample to the first invariant is your create → delete → re-append interleaving, with the destruction visible on one line:

[State 3] readAtCurrentEpoch  observedAt=2 observed=false  tombstoneEpochs=Set(2)
[State 4] appendSegment       epoch=3      segmentEpochs=Set(1, 3)
                                           tombstoneEpochs=Set()   <-- delete destroyed
[State 5] rereadFirstEpoch    observedAt=2 observed=true           <-- answer flipped

m2_epoch_scoped_read_test.qnt holds four deterministic scenarios mirroring the e2e repros; all four pass against the intended module under quint test.

Modeling note worth keeping

The first three drafts of the intended model failed their own invariants. Each time the cause was the same: a scalar where storage has history. A single segmentEpoch can't express that appends accumulate; a single pointEdgeEpoch can't express two point writes; a single tombstoneEpoch can't express two deletes. All three had to become sets before the intended contract could even be stated. That is the bug restated in miniature — the implementation keeps scalars where correctness needs history.

Both attempts pass, but neither is a proof of safety. The repros run against InMemory object storage where each commit lands in its own WAL file, so the batched-commits-in-one-file case the analysis describes never arose. Deciding it needs what the original scoping called for: a delayed-WAL-PUT object-store wrapper that holds flushes open, or Jepsen. Both tests are committed and #[ignore]-marked so they can be re-pointed at that harness rather than rewritten.

Local environment caveat

The graphblas-gated tests could not be exercised through the compiled GraphBLAS kernel on this machine: SuiteSparse 7.12.2 / libgraphblas 10.3.1 rejects the calls the code makes (GxB_Desc_set_INT32 returned GraphBLAS status -3). This is a pre-existing version incompatibility — 17 existing tests fail the same way with --features graphblas, independent of any change here. The WAL-tail repros therefore assert directly on the tail overlay, which is pure Rust and is where the suspected hole lives; the compiled CSC payload plays no part in whether the overlay covers the commit window. The default suite is unaffected: 90 passed, 0 failed, 4 ignored.
