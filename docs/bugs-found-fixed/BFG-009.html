BFG-009 — epoch-scoped reads compose over unpinned live state

An epoch-scoped read is not a pure function of its epoch. Later writes rewrite the answer to an earlier question, so an acknowledged delete can be retroactively erased, and a read can return edges committed after its own epoch.

P0 · confirmed-bug status: open · no fix applied data-loss class 3 e2e repros Quint model: M2
↓ Skip to “Verify it yourself”

What the bug is

Turbolay lets a caller read the graph as of a storage epoch. The visibility rule for segment adjacency is:

a segment edge is visible at read_epoch  when  segment.storage_sequence <= read_epoch
a tombstone suppresses it                when  tombstone_epoch          <= read_epoch

That rule is sound only when it is evaluated against storage state pinned at read_epoch. Several read paths evaluate it against live state instead — whatever storage happens to contain at the moment the scan runs, which may be many commits ahead of the epoch that was asked about.

On its own that would be survivable if storage kept every record forever. It does not. Two writer behaviours actively destroy the history the evaluation depends on, and the composition of “unpinned evaluation” with “destroyed history” is the bug: the same call, with the same epoch argument, returns a different answer depending on what has been written since.

Why it happens — root cause

Writer behaviour 1 — a re-append deletes the tombstone key

When a trusted segment append re-inserts a destination, it clears any tombstone standing against that (src, dst) pair — src/shard/write.rs:4279:

if inserted > 0 {
    mark_adjacency_dirty_txn(&txn, cell_id, edge_type, end_epoch)?;
    for dst in &inserted_dsts {
        txn.delete(keys::out_segment_tombstone(cell_id, edge_type, src, *dst).as_bytes())?;
    }

This is correct for current reads — the edge is back, so the tombstone must go. But the tombstone was the only record that a delete had ever been acknowledged at some earlier epoch. Once it is gone, any later evaluation of “was this edge present at epoch N?” over live state finds a segment at epoch 1 and no tombstone at all, and answers true — for an epoch at which the delete had already been acknowledged to a client.

Writer behaviour 2 — the point-edge branch has no epoch filter

The read composition edges_at → canonical_adjacency_at → current_matrix_rows (src/engine/artifact_build.rs:488-532) does three separate live prefix scans. The segment scan filters on storage_sequence > base_epoch → continue. The point-edge scan, at src/engine/artifact_build.rs:497-506, filters on nothing:

let prefix = keys::out_edge_type_prefix(cell_id, edge_type);
let mut iter = self.scan_remote_prefix(&prefix).await?;
while let Some(kv) = iter.next().await? {
    let key = String::from_utf8_lossy(&kv.key).into_owned();
    let record = decode_edge_record(&key, &kv.value)?;
    rows.push(record.src, record.dst);            // <-- base_epoch never consulted
    ensure_limit(
        "build_matrix_tiles_edges",
        rows.raw_edges,
        self.limits.max_artifact_build_edges,
    )?;
}

The base_epoch parameter is in scope and is used two statements later for tombstones and segments. It is simply never applied to point edges. The same shape appears in out_neighbors_in_storage_snapshot at src/shard/query.rs:135-142. Point-edge records carry no epoch of their own, so there is nothing to filter on — which is why fix direction 3 below is the expensive one.

Neither branch pins a snapshot when it is called outside scope_snapshot. Meanwhile segment compaction also deletes tombstones and rewrites segment sequences (src/shard/maintenance.rs:207-229). Every one of these operations is correct for a current read. Together they mean the _at APIs promise history the storage layer deliberately does not keep.

EXPRESSION 3 · concurrency stress, ~17s

Current-epoch reads contradict acknowledged history

current_epoch_reads_match_acknowledged_history_under_concurrent_reinserts — src/tests.rs:12097

One writer task cycles acknowledged delete_edge / segment re-append on a single edge, recording each acknowledged (epoch, state) pair. A reader loop of 4 000 iterations derives current_epoch() and immediately calls edge_exists_at at that epoch — the exact query_read_epoch-then-read composition the server paths use. The check only judges reads whose epoch the acknowledged history already covers.

603 current-epoch reads contradicted acknowledged history; first:
(read_epoch, expected, observed) = Some((6, false, true))

603 of 4 000 reads — 15% on the run recorded here; the finding doc recorded 681 (17%) on an earlier run. The count is timing-dependent and varies per run, but it has never been zero. A read anchored at epoch 6 observed an edge whose delete was acknowledged at epoch 6. In Jepsen terms: a read-your-writes violation for the deleting session, and a set-full resurrection — present → acknowledged-absent → present.

Blast radius — and what is safe

Safe — the main cypher rows path

execute_parsed_opencypher_rows (src/shard/query.rs:461-476) takes one snapshot, derives read_epoch from that snapshot (let read_epoch = snapshot.seq();), and runs the whole query inside GraphStore::scope_snapshot. Its live scans therefore resolve against pinned state, which is exactly what the visibility rule requires. Indexer builds are safe for the same reason: build_graph_index runs canonical_adjacency_at(base_sequence) inside scope_snapshot with base_sequence == snapshot.seq(), which neutralises both unpinned branches. This is the pattern the broken paths should copy.

  • The _at APIs — edge_exists_at, out_neighbors_at, out_degree_at, edges_at. The direct expression of expressions 1 and 2. The epoch is accepted unvalidated and answered from live state.
  • Kernel / streaming page fast paths (src/shard/query.rs:4475, :4607) derive read_epoch from a snapshot that is then dropped (query_read_epoch, src/shard/query.rs:4495), and their storage fallback takes its own fresh snapshot — reachable_from_storage_frontier, src/shard/query.rs:4894 — with no seq() == read_epoch guard. Any delete-plus-re-append, or any point write, committing between those two lines tears the composition inside a single page. The compiled path does guard (storage_snapshot.seq() != read_epoch → return Ok(None), src/shard/query.rs:5268) — but the fallback it lands on is the unguarded one.
  • validate_cell_edge_type (src/shard/query.rs:6059) reads current_epoch and then edges_at unpinned. Its repair report is subject to the same race and can report degree mismatches that were never real.

Checked and ruled out

Each of these was a plausible alternative explanation and was eliminated against the source, so the diagnosis above is not the last theory standing by default.

  • Forced-sequence commits. commit_txn_strict pins the commit sequence to seqnum()+1 (src/codec.rs:143-159), so epochs really are commit sequences. Not a numbering artefact.
  • Segment-scan early break. Segment keys zero-pad the sequence (src/keys.rs:67-74), so lexicographic order is numeric order and the scan does not terminate early on a valid segment.
  • Segment compaction atomicity. Compaction is atomic and preserves out-of-range tombstones and live-at-epoch semantics (src/shard/maintenance.rs:189-248). It contributes to history destruction but is not itself incorrect.
  • DETACH DELETE coverage. It scans segments as well as point edges (src/shard/write.rs:739-773), so this is not a delete that simply missed the segment representation.
  • Indexer builds. Consistent, for the scope_snapshot reason given above.

Fix directions

Not applied

Nothing below has been implemented. fix_commit is none and the finding is open. The three regressions are recorded so that a fix has something to be judged against; per validation-protocol.md, they must pass at the fix commit and their #[ignore] markers must then be removed. A bisect for introduced_or_first_bad_commit is still pending.

  1. Pin or reject. Pin every epoch-scoped read to a storage snapshot whose seq() == read_epoch, or reject the request with SnapshotAhead / UnsupportedQuery the way snapshot_at already does (src/shard/lifecycle.rs:620-639). This is the cheap fix, and it makes the API honest about the history storage actually keeps.
  2. Derive the epoch from the snapshot you traverse. In the kernel and streaming page paths, take the snapshot first and use its seq(), mirroring execute_parsed_opencypher_rows. This closes the torn-page window without any storage-format change.
  3. Stop destroying history — only if historical epoch answers are a genuine product requirement. Tombstone keys must not be deleted on re-append (write a supersede record instead), and point edges need an epoch-carrying record. This is a much larger change; 1 + 2 restore correctness without it.

What the Quint model does and does not prove

Three modules in quint-models/turbolay/, following the existing M-family convention.

m2_epoch_scoped_read.qnt is the intended contract: every append, point write, and tombstone is retained as a set, so any epoch can be reconstructed. It states three invariants and holds all of them, with all four witnesses reachable so nothing is holding vacuously:

  • epochScopedReadIsStable — re-reading an already-answered epoch gives the same answer, however many commits landed later.
  • readNeverSeesTheFuture — the answer equals the state reconstructed at the read epoch.
  • readMatchesAcknowledgedHistory — a read anchored at an acknowledged epoch agrees with that acknowledgement.

m2_epoch_scoped_read_buggy.qnt encodes the two implementation behaviours — the re-append deleting preceding tombstones (write.rs:4279) and the unfiltered point-edge branch (artifact_build.rs:497-506). It violates two of the three invariants.

InvariantIntendedFault modelDiscriminates?
epochScopedReadIsStableholdsviolatedYes
readNeverSeesTheFutureholdsviolatedYes
readMatchesAcknowledgedHistoryholdsholdsNo
Be precise about this — the model is narrower than the evidence

The third invariant is not discriminated, and that is a limit of the module, not a weakness in the e2e evidence. In the model a read is atomic: the epoch is derived and the state is evaluated in a single action. Every write action advances epoch and sets ackedEpoch to the new epoch, so observedAt == ackedEpoch is only ever tested against the very state that produced the acknowledgement — and it always agrees.

Expression 3 fails for exactly the reason this model cannot express: query_read_epoch and the read are separate steps, and a writer commits between them. Discriminating expression 3 formally requires a module with a non-atomic read (derive-epoch and read-at-epoch as two distinct actions). That module has not been written. So: the model proves expressions 1 and 2 are real contract violations rather than mis-stated tests; expression 3 rests on its e2e reproduction alone.

The shortest counterexample to epochScopedReadIsStable is the create → delete → re-append interleaving, at five steps — --max-steps=4 finds none. Step 9 below reproduces it exactly.
