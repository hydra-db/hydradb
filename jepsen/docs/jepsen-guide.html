1. What Jepsen is

Jepsen is not a fuzzer and not a load generator. It is a falsification harness: it drives a real distributed database from outside, records a totally-ordered history of every request and response, injects faults while doing so, and then asks an offline checker whether that history could have been produced by a correct system.

The three moving parts:

The history
Every operation is logged twice — an :invoke when the client sends it and an :ok / :fail / :info when it resolves. The gap between the two is the window in which the operation may have taken effect.
The nemesis
A special client whose "operations" are faults: kill a process, partition the network, skew a clock, pause a node with SIGSTOP. Faults are scheduled into the same history, so the checker can correlate an anomaly with the fault that caused it.
The checker
A pure function from history to verdict. Because it runs offline over the recorded history, it can afford search that would be impossible online — Knossos explores possible linearizations; Elle infers a dependency graph and looks for cycles.
The key idea. A green Jepsen run proves nothing. A red one proves something concrete and reproducible: here is a history the database produced that no correct implementation could have produced. Design tests to fail, not to pass.

The :info outcome is the whole game

Most testing frameworks have two outcomes. Jepsen has three, and the third is what makes it sound. When a write times out, the client does not know whether it committed. Recording that as :fail would let a real lost update hide; recording it as :ok would produce false alarms. :info means indeterminate — the checker must consider both worlds. Every client you write must classify errors correctly, or the results are meaningless.

; From jepsen/turbolay/src/jepsen/turbolay/http.clj
(catch SocketTimeoutException e   (assoc op :type :info, :error :timeout))
(catch ConnectException e         (assoc op :type :fail, :error :connection-refused))
;; 4xx  -> definitively rejected, nothing was mutated  -> :fail
;; 5xx  -> server may have applied it before dying     -> :info

2. Anatomy of a test

A Jepsen test is a Clojure map. Six keys carry the weight:

KeyRoleIn this suite
:dbInstall / start / stop / kill / pause the database on each nodeturbolay/db.clj — launches graph-node with the S3 env, waits on /readyz
:clientTurn abstract ops into real requestshttp.clj + one workload ns; POSTs Cypher to /v1/graphs/default/query
:generatorLazy tree of ops handed to worker threadsPer workload; mixed reads/writes, rate-limited by gen/stagger
:nemesisFault injectornemesis.clj — standard faults plus an object-store partition
:checkerHistory → verdictset-full, Knossos linearizability, custom session checker
:osNode OS setupDebian/Ubuntu containers

The lifecycle: setup DB → run generator (clients and nemesis concurrently) → heal → quiesce → final read → teardown → check. The final read matters: it runs after all faults have healed and the cluster has had time to settle, so anything still missing is definitively lost, not merely delayed.

3. Consistency models you can actually test

Jepsen checks against models, and models form a lattice. Testing against a model stronger than the database claims produces noise; weaker produces false confidence.

ModelInformal statementChecker
LinearizableEvery op appears to take effect atomically at some instant between invoke and complete; reads see the latest committed writeKnossos (checker/linearizable)
SequentialSome total order exists that respects each process's own order, but not real timeElle
Snapshot isolationTransactions read a consistent snapshot; no write-write conflictsElle (:consistency-models [:snapshot-isolation])
Read-your-writesA session never fails to see its own acknowledged writesCustom / Elle session checks
Monotonic readsA session never un-sees something it already sawCustom
Grow-only setAcknowledged elements are never lost; reads are subsets of what has been addedchecker/set-full
Start with the set. set-full is the highest-value-per-line checker in Jepsen. It is cheap, it never gives false positives, and it catches the failure everyone actually fears: an acknowledged write that vanishes. Reach for Knossos and Elle after the set workload is clean.

4. The checkers, concretely

set-full

Ops are {:f :add :value v} and {:f :read :value #{...}}. The checker classifies each added element:

  • ok — acknowledged and present in the final read
  • lost — acknowledged (:ok) but absent from a later read. Always a bug.
  • recovered — reported :fail but present anyway. Also a bug — a failed write applied.
  • stale — present, then absent from a later read, then present again. Legal under weak consistency, a violation under strong.

It also reports stale-count and duplicated elements, which is how you catch a WAL-tail-plus-index merge that double-counts an edge.

Knossos linearizability

Given a single-register model with reads and writes, Knossos searches for a linearization of the history. It is exponential in concurrency, so keep it to a handful of threads per key — hence jepsen.independent, which runs many small independent registers in parallel and checks each separately. If it finds no valid linearization, it emits an SVG showing the exact operations that cannot be ordered.

Elle

For transactional systems. Elle infers write-write, write-read, and read-write dependencies from the values transactions observe, builds a graph, and reports cycles — each cycle type maps to a named anomaly (G0 dirty write, G1c circular information flow, G2 anti-dependency cycle). It scales far better than Knossos. Turbolay's HTTP API is auto-commit only today, so Elle's transactional power is mostly unused here; that changes the day multi-statement transactions ship.

Custom session checker

Turbolay's causal mode plus bookmarks is a session-guarantee claim, and no stock checker encodes it. causal.clj folds the history per session and asserts two things: a read carrying an acknowledged write's bookmark must observe that write (read-your-writes), and a session's reads must never lose a previously observed element (monotonic reads).

5. What Turbolay claims, restated as testable propositions

Turbolay is not a Raft cluster. Its architecture makes some Jepsen faults irrelevant and one fault unusually important.

  • The object store is the source of truth. SlateDB owns writer fencing, WAL durability, and commit ordering.
  • One writer per graph store; any number of reader processes. Nodes are stateless and controllerless — any node may lazily open the (fenced) writer.
  • Reads come in exactly two modes. causal serves from the node's local durable view, refreshing only when a supplied bookmark demands it. strong refreshes the SlateDB reader from object storage first, then pins one snapshot.
  • Reads combine an indexed base with the committed WAL tail when the async CSC indexer lags.

Turned into propositions a checker can falsify:

#PropositionFalsified by
P1An acknowledged write is never lost, regardless of which node accepted it or what happened nextset-full reporting lost
P2Two nodes racing to open the writer never both commit — fencing holdslost or duplicated elements around a kill/pause
P3A strong read observes every write committed before its refreshKnossos linearizability violation
P4A causal read carrying a bookmark observes the write that produced it, on any nodesession checker read-your-writes violation
P5Reads never regress within a sessionsession checker monotonic-reads violation
P6The indexed-base + WAL-tail merge never duplicates or drops an edgeset-full duplicated, or set-size mismatch while the indexer lags
P7A node cut off from S3 either serves a stale-but-legal view or errors — it never serves a wrong oneobject-store partition + strong reads returning :ok with missing data
The fault that matters most here is not a network partition between nodes. Turbolay nodes barely talk to each other. The dangerous configuration is a node partitioned from the object store while still reachable by clients: it can still accept connections and still answer from its local cache. That is why this suite ships a custom object-store nemesis that iptables-drops MinIO on a subset of nodes.

6. What the first runs found

Three things surfaced before a single fault was injected. All three are worth recording, because two were harness bugs and one is a genuine operational constraint — and telling those apart is most of the work in Jepsen.

Writer-affinity thrash real

Jepsen spreads client operations across all nodes by default. Against a single-writer store that means five nodes racing to open the SlateDB writer, fencing each other continuously. The first run produced 80 l0_manifest_writer error=Fenced events and HTTP 500s on two thirds of all writes.

Fencing itself was correct — lost-count 0, no duplicates. Nothing was unsafe. But write throughput collapsed, and a test that only re-measures thrash cannot find anything else.

The operational lesson: a client that fans writes across nodes will see most of them fail. Real clients must follow the Bolt routing table to the current writer. The suite now models this in routing.clj — writes go to one node and advance on failure — which is also what makes killing that node a meaningful handover test rather than noise.

Requested timeout above the server cap is rejected, not clamped real

Every read returned 429 resource_exhausted. The client asked for timeout_ms: 30000 while the node was configured with GRAPH_MAX_QUERY_RUNTIME_MS=20000. The service rejects an over-cap request outright (src/client/service.rs:774) rather than clamping it to the maximum.

Defensible, but sharp: a client with a generous default timeout gets zero successful queries against a conservatively configured node, and the error says "resource exhausted" — which reads like load shedding, not a misconfiguration.

nemesis-package always constructs every fault harness

jepsen.nemesis.combined/nemesis-packages builds all five stock packages regardless of :faults; only the generators are gated. The file-corruption nemesis downloads an x86_64-only bitflip release from GitHub in setup!, so on arm64 nodes — or any host without egress — the run aborts before issuing a single operation, even with --nemesis none. nemesis.clj selects packages by hand instead.

Server cursors are bound to a query_id real

Paginated reads failed with 400 invalid_request: result cursor does not belong to this query request. The client omitted query_id, so the server generated a fresh one per HTTP request — and page 2's cursor no longer matched the query that created it.

This one is dangerous precisely because of how it fails. A truncated read is not an error to set-full; it is evidence of catastrophic data loss. A harness that silently stops at page 1 will confidently report a database bug that does not exist. Every page of one logical query must now carry the same client-generated query_id.

State leaked between runs harness

teardown! clears the local SlateDB cache, but the object store is the source of truth — so it survived. Worse, the run-scoped object prefix keyed off :run-id, which is not a real Jepsen test key, so every run silently shared one path. Run N's edges were still present in run N+1, which is what pushed result sets past the page size and exposed the cursor bug above.

For a database whose durable state lives outside the nodes, "tear down the nodes" is not "reset the database". turbolay-test now stamps a real per-run id into the test map.

The two phantom data-loss bugs harness

The first fault run reported lost-count 426 — essentially every acknowledged write. That magnitude is itself the clue: total loss of everything acknowledged is far likelier to be a harness defect than a database one. Two separate bugs were behind it.

A run-id recomputed per test-map construction. The object-store prefix came from (System/currentTimeMillis) evaluated inside the test-builder, and the test map is built more than once per lein run. setup! opened the database at one prefix; a later nemesis restart opened a different, empty one. The final reads found an empty graph. The object store settled it: the original prefix held 855 objects with writes right up to the end of the run — nothing had been lost at all. The fix is a top-level def, evaluated once per JVM.

A stale pidfile. cu/grepkill! kills the process but leaves /var/run/graph-node.pid, so the next start-stop-daemon matched the stale file and reported :already-running without starting anything. The nemesis logged a healthy heal while the port stayed closed, and every post-fault read came back :connection-refused. Use cu/stop-daemon!, which removes the pidfile. A bounded /readyz wait was added to start! for the same reason — db-nemesis fires :start and moves on without waiting for the listener to bind.

Baseline, once those were fixed: 592 adds, 577 reads, 0 failures, 0 indeterminate, lost-count 0, stale-count 0, duplicated-count 0.

Under process kills: 405 acknowledged adds, all stable; 160 writes correctly reported :fail as the writer was killed; lost-count 0, stale-count 0, duplicated-count 0. Writer fencing and handover held.

Note the ratio: five of the seven problems found so far were in the test harness, not the database. That is normal, and it is the entire argument for the escalation ladder — every rung you skip is a harness bug you will later mistake for a distributed-systems bug. Two independent harness defects here manufactured a 426-write "data loss" that never happened.

Three things are worth drawing out of those numbers.

P1 and P2 hold under both kill and pause, and pause is the stronger result. A SIGKILL'd process cannot do damage; a SIGSTOP'd one resumes holding a stale writer handle and a cached epoch and tries to keep writing. Zero lost and zero duplicated across both means SlateDB's epoch fencing survives the case it exists for.

P7 holds, and this is the most valuable single result. Under object-store partition roughly 40% of reads became indeterminate and none became stale. A node cut off from S3 but still accepting client connections errors rather than quietly answering from its local cache. That is the failure that would be most dangerous in production and least likely to be noticed — a server that looks healthy and returns confident, wrong answers.

Nothing was ever spuriously acknowledged. recovered-count stayed 0 across every fault run: no write that reported :fail was later found present. That matters as much as the lost-write result — a database that applies writes it told you it rejected is just as broken as one that drops writes it accepted.

The bookmark contract survives node-hopping. Every one of the 21 causal sessions moved to a randomly chosen node on every single operation, and not one failed to observe its own acknowledged write or lost an element it had already seen. A session pinned to one node could not have detected a broken bookmark; these were not pinned.

The most informative number in the suite

stale 235 under causal — stale 0 under strong. Under faults of equal severity, the causal run recorded 235 stale observations (an element present, then absent, then present again) while all five strong runs recorded none.

That is not a defect. set-full here runs with :linearizable? false, and staleness is precisely what causal consistency permits and strong consistency forbids. It is the most valuable result in the suite because it is positive evidence rather than an absence of failure: the two documented read modes are not merely labelled differently, they behave measurably differently, in exactly the documented direction.

Consider the counterfactuals. A causal mode reporting stale 0 would suggest it was quietly paying for strong reads and giving up the performance the mode exists to provide. A strong mode reporting stale > 0 would be a straightforward correctness bug. Neither happened — which is the sort of claim a checker can support and a benchmark cannot.

7. The three workloads

edge-set P1 P2 P6 P7

A grow-only set built out of edges. Writers CREATE (root)-[:E]->({id: v}) with a unique v; readers scan the root's full outbound adjacency, paging through server cursors until exhausted. Checked with set-full.

add:  CREATE (a {id: 1})-[:E]->(b {id: $v})
read: MATCH  (a {id: 1})-[:E]->(b) RETURN b.id AS v

This is the primary test. It exercises the write path, writer fencing, the WAL, the CSC index publication, generation GC, and paging — all at once — and any anomaly it reports is unambiguous.

register P3

Many independent single-key registers held in a vertex property, read and written with strong consistency and checked by Knossos for linearizability. This is the direct test of the strong-read claim.

write: MERGE (u {id: $k})-[:ANCHOR]->(a {id: 999999999})
       MATCH (u {id: $k}) SET u.val = $v
read:  MATCH (u {id: $k}) RETURN u.val AS v

causal P4 P5

Same grow-only set, but every operation is deliberately sent to a random node while the client carries its bookmark forward. A session that never moves between nodes cannot detect a broken bookmark, which is exactly why this workload keeps moving.

8. The fault schedule

FaultMechanismWhat it probes
killSIGKILL graph-node, restartWriter handover, epoch fencing, WAL recovery
pauseSIGSTOP / SIGCONTThe nastier case — a "dead" writer that comes back believing it is still the writer
partitioniptables between nodesRouting-table and discovery behaviour
object-storeiptables drop toward MinIOThe important one: durability path severed, serving path intact
clockbump / strobe node clocksAny lease, TTL, or timestamp that fencing secretly depends on

pause deserves emphasis. A killed process cannot do damage. A paused one resumes with stale in-memory state — an open writer handle, a cached epoch — and tries to keep writing. If fencing is going to fail anywhere, it fails there.

9. Running the suite

# 0. Build the graph-node runtime image (from the repo root)
docker build --target runtime -t turbolay:jepsen .

# 1. Bring up MinIO + 5 DB nodes + the Jepsen control node
cd jepsen/docker
docker compose up -d --build

# 2. Run a test from the control container
docker compose exec control lein run test \
  --workload edge-set \
  --consistency strong \
  --nemesis kill,pause,object-store \
  --time-limit 300 \
  --concurrency 20

# 3. Browse results
docker compose exec control lein run serve   # http://localhost:8080

A useful escalation ladder — never start at the top:

  1. --nemesis none, edge-set. If this fails, the bug is not a distributed-systems bug and Jepsen is the wrong tool to debug it.
  2. --nemesis kill. Writer handover under clean death.
  3. --nemesis pause. Writer handover under unclean death — the fencing test.
  4. --nemesis object-store. Durability severed, serving intact.
  5. --workload register --nemesis kill,pause. Linearizability of strong.
  6. --workload causal --nemesis kill,partition,object-store. Bookmark contract.
  7. Everything at once, long duration, for soak.

10. Reading the results

Each run writes to store/<test-name>/<timestamp>/:

results.edn
The verdict. :valid? true / false / :unknown, plus per-checker detail.
history.txt
The full operation log. This is the evidence; everything else is derived from it.
jepsen.log
Harness log, including every nemesis action with timestamps.
latency-raw.png, rate.png
Latency and throughput with fault windows shaded — often the fastest way to see when things went wrong.
linear.svg
Only on a linearizability failure: the minimal non-linearizable operation set.
graph-node.log
Per-node server logs, pulled back by db/LogFiles. Correlate a lost element's timestamp against these.
:valid? :unknown is not a pass. It usually means the checker timed out (Knossos on too much concurrency) or too many ops were :info to conclude anything. Reduce concurrency or shorten the run and re-check.

11. Pitfalls that produce false results

  • Misclassifying errors. A timeout recorded as :fail will hide real lost updates. When in doubt, :info.
  • Reads that don't read everything. If the final read is paginated and you stop at the first page, set-full reports a catastrophic data-loss bug that does not exist. This client loops cursors to exhaustion.
  • Not healing before the final read. Every anomaly becomes "lost" if the cluster is still broken when you look.
  • Too much concurrency for Knossos. Twenty threads on one key will not finish. Use jepsen.independent and ~5 threads per key.
  • Testing a stronger model than is claimed. Running Knossos against causal reads will "find" violations that are entirely legal.
  • Clock skew without SYS_TIME. The nemesis silently no-ops in an unprivileged container, and you conclude the system tolerates skew when it was never tested.
  • Short runs. Real anomalies need a fault to land inside a specific narrow window. Ten minutes finds things that ninety seconds never will.

12. Reading list

Start here

  • jepsen.io/consistency — the interactive consistency-model lattice. The single best 20 minutes you can spend before writing a test.
  • Official Jepsen tutorial — builds an etcd test from nothing. Follow it end to end once; every later test is a variation.
  • Jepsen analyses index — ~40 real reports. Read the ones for systems closest to yours.

Most relevant analyses for an object-store-backed, single-writer engine

  • Datomic Pro — single-writer transactor over shared durable storage. The closest architectural analogue to Turbolay in the whole corpus.
  • Dgraph 1.1.1 — a distributed graph database; useful for what graph-specific anomalies look like.
  • etcd 3.4.3 — the canonical clean example of a well-scoped test.
  • MongoDB 4.2.6 — the definitive study of how read-concern / write-concern levels interact, which is the same shape as causal vs strong.
  • Redpanda 21.10.1 — object-store-adjacent log storage under fault injection.

Theory worth the time

  • Elle: Inferring Isolation Anomalies from Experimental Observations (Kingsbury & Alvaro) — how Elle recovers dependency graphs from black-box observations.
  • Herlihy & Wing, Linearizability — the original definition Knossos implements.
  • Session guarantees — read-your-writes and monotonic reads, defined precisely. Directly relevant to the bookmark contract.
  • Bailis et al., Highly Available Transactions — which guarantees survive partitions and which cannot.

Talks

  • "Jepsen VII: The Cybernetic Special" — Kyle Kingsbury on the method itself.
  • "Testing Distributed Systems with Deterministic Simulation" (FoundationDB) — the complementary technique; worth knowing where each approach wins.

API reference

  • Jepsen on cljdoc — jepsen.checker, jepsen.generator, jepsen.nemesis.combined, jepsen.independent.
  • jepsen-io/elle and jepsen-io/knossos.
  • Generator guide — generators are the least intuitive part of the framework; this doc is essential.
